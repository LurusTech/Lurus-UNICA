## 1 系统架构与组件清单

### 1.1 总体结构

```
渠道平台（微信 / 淘宝 / 快手 / 小红书）
        │  HTTPS 回调
        ▼
   gateway ──写入──► Redis 流 unica:inbound ──► router ──► Dify（大模型服务 + 知识库）
     ▲  │                                         │
     │  └◄── Redis 流 unica:outbound ◄────────────┤  （AI 答复、坐席回复）
     │                                            └──► Redis 流 unica:handoff ──► router 转人工处理 ──► Chatwoot
     │
     └── Chatwoot 坐席回复回调（/api/v1/webhook/chatwoot）

运营门户 portal（静态页面）──/api/──► admin ──► PostgreSQL / Redis / Dify 控制台接口 / Chatwoot 平台接口
reporter ──► PostgreSQL（报表查询）
Prometheus ◄── 各服务 /metrics；Alertmanager ──► webhook-adapter ──► 钉钉 / 企业微信 / 飞书
```
<!-- 依据: README.zh-CN.md:7-15; unica/gateway/internal/stream/producer.go:17-26; unica/router/internal/routing/router.go:29-35; unica/router/internal/handoff/consumer.go:20; unica/gateway/cmd/gateway/main.go:96-124; deploy/monitoring/prometheus-values.yaml:142-163 -->

系统是多租户的。一个"租户"在代码和数据库里叫"产品线"（product line），一条产品线对应一个 Dify 应用和一个知识库数据集，可选对应一个 Chatwoot 账号。<!-- 依据: README.zh-CN.md:5,25 -->

### 1.2 一条消息的处理过程

1. 渠道平台把客户消息推送到 gateway 的回调地址。gateway 验签、转换为统一格式，写入 Redis 流 `unica:inbound`。<!-- 依据: unica/gateway/internal/adapter/wechat/handler.go:57-82; unica/gateway/internal/stream/producer.go:40-69 -->
2. router 以消费组 `router-group` 读取 `unica:inbound`，按消息中的渠道 ID 查找所属产品线。查不到时记录日志 `failed to resolve route for channel ...` 并丢弃该消息。<!-- 依据: unica/router/internal/routing/router.go:368-375; unica/router/internal/routing/cache.go:87-118 -->
3. 会话处于 AI 处理状态时，router 调用该产品线的 Dify 应用，再由判定链路决定"发给客户"还是"转人工"。Dify 调用失败或返回空答复时，直接转人工。<!-- 依据: unica/router/internal/routing/router.go:858-895 -->
4. 发给客户：router 写入 `unica:outbound`，gateway 以消费组 `gateway-outbound` 读取并调用渠道平台接口发送。发送失败按退避重试，耗尽后写入死信流 `unica:dead-letter`。<!-- 依据: unica/gateway/internal/stream/producer.go:20-25; unica/gateway/internal/stream/consumer.go:170-196; unica/gateway/internal/dedup/retry.go:46-79; unica/gateway/internal/dedup/deadletter.go:16-19 -->
5. 转人工：router 写入 `unica:handoff`，由 router 内的转人工处理器在 Chatwoot 中建联系人和会话、写摘要备注、尝试分配坐席。<!-- 依据: unica/router/internal/handoff/handler.go:79-135 -->
6. 会话已转人工后，客户的新消息由 router 直接转发到对应的 Chatwoot 会话。<!-- 依据: unica/router/internal/routing/router.go:446-455 -->
7. 坐席在 Chatwoot 中回复，Chatwoot 回调 gateway 的 `/api/v1/webhook/chatwoot`。gateway 按 Chatwoot 会话上的属性找到 UNICA 会话、渠道与客户的平台用户 ID，写入 `unica:outbound`，再发给客户。<!-- 依据: unica/gateway/internal/webhook/chatwoot.go:300-404,493-565; unica/router/internal/handoff/handler.go:323-363 -->

### 1.4 关于"判定链路"（judge）

判定链路负责对每条 AI 答复做护栏判断、本体校验、空答复拦截，并决定发送或转人工。判定逻辑在共享代码 `unica/pkg/judge/` 中，由 router 进程内调用（`unica/router/internal/routing/judge.go` 只做输入转换）。它不是独立服务，没有独立进程、端口或镜像。<!-- 依据: unica/router/internal/routing/judge.go:10-19; unica/pkg/judge/judge.go:166-195 -->

仓库中另有一个独立的命令行工具 `unica/judge/`（判定闸门与对话"体检"报告工具，与 router 调用同一套判定逻辑）。它不属于本系统的运行组件：不需要部署，没有镜像，`make docker-build` 也不构建它。本手册不涉及它的运维。<!-- 依据: unica/judge/README.md:1-3,35; unica/Makefile:1-3 -->

## 3 日常运维

### 3.1 启停与重启顺序

**启动顺序**（依赖在前）：

1. PostgreSQL、Redis
2. Dify（ssrf-proxy、sandbox、api、worker、web、nginx）
3. Chatwoot（web、sidekiq）
4. admin
5. router
6. gateway
7. reporter
8. 门户 nginx

依据：admin、router、reporter 启动时连不上 PostgreSQL 会直接退出；gateway、router、admin 连不上 Redis 会直接退出。router 在启动消费者之前先补建当月及后续月份的分区。本地环境脚本的启动顺序也是 admin、router、gateway。<!-- 依据: unica/admin/cmd/admin/main.go:140-163; unica/router/cmd/router/main.go:40-63,74-78; unica/reporter/cmd/reporter/main.go:30-35; unica/gateway/cmd/gateway/main.go:42-54; scripts/start-local-env.sh:183-186 -->

**停止顺序**与启动相反：先停 gateway（不再接收回调），再停 router、admin、reporter，然后是 Chatwoot、Dify，最后是 Redis、PostgreSQL。

**优雅退出**：四个服务都在收到 SIGTERM 或 SIGINT 时优雅退出。

| 服务 | 退出过程 | 最长耗时 |
|---|---|---|
| gateway | 停止 HTTP → 停出站消费 → 停令牌刷新 → 处理积压的出站消息 → 关闭连接 | `GATEWAY_SHUTDOWN_TIMEOUT`（默认 30 秒）+ 10 秒 |
| router | 停 HTTP → 停转人工消费 → 停消息处理 → 停开关轮询、状态管理、分区维护 | HTTP 部分 10 秒 |
| admin | 停 HTTP | 15 秒 |
| reporter | 停 HTTP | 10 秒 |

<!-- 依据: unica/gateway/cmd/gateway/main.go:238-282; unica/gateway/internal/config/config.go:66; unica/router/cmd/router/main.go:247-285; unica/admin/cmd/admin/main.go:676-693; unica/reporter/cmd/reporter/main.go:73-87 -->

编排层给 gateway 的强制终止等待时间，建议不少于 40 秒（30 秒 + 10 秒）。

**单个服务重启的影响：**

- gateway：重启期间渠道回调失败，平台是否重推取决于各平台规则。已写入 `unica:outbound` 但未发出的消息留在流中，重启后继续处理；其它实例遗留的未确认消息每 `GATEWAY_PENDING_CLAIM_INTERVAL`（默认 60 秒）认领一次。<!-- 依据: unica/gateway/internal/config/config.go:65; unica/gateway/internal/stream/consumer.go:141-147 -->
- router：重启期间客户消息留在 `unica:inbound`，重启后继续处理；每个工作协程启动时先处理本消费者名下未确认的消息（日志 `recovered N pending message(s)`）。请保持 `ROUTER_CONSUMER_NAME` 不变，否则旧名下的未确认消息不会被新名字接手。<!-- 依据: unica/router/internal/routing/router.go:329-345; unica/router/cmd/router/main.go:346 -->
- admin：门户暂时不可用。登录令牌是签名令牌，重启后仍有效（`JWT_SECRET` 不变的前提下）。
- reporter：报表暂时不可用，不影响对话。

**Dify、Chatwoot 重启**（执行位置：可访问 K8s 集群的运维机；命名空间按仓内清单为 `unica-dev`）：


### 3.3 升级

UNICA 自有服务的升级步骤：

1. 确认本次版本新增了哪些迁移编号。【待填：版本发布说明的获取方式】
2. 按第 5 章做一次完整备份，并确认备份可读。
3. 构建或获取新镜像（2.2）。
4. 停 gateway，再停 router、admin、reporter（3.1）。
5. 逐个执行新增的迁移文件。执行位置：装有 `psql` 的运维机，仓库根目录。
   ```bash
   psql "$POSTGRES_URL" -v ON_ERROR_STOP=1 -f unica/router/migrations/【待填：新增迁移文件名】.sql
   ```
6. 按 admin、router、gateway、reporter 的顺序启动新版本。
7. 验证：4.1 的健康检查全部通过；router `/configz` 的开关符合预期；门户能登录；用测试账号从一个渠道发一条消息，确认收到答复。
8. 回滚：迁移没有回滚脚本。回滚 = 恢复第 2 步的数据库备份 + 换回旧镜像。

<!-- 依据: README.zh-CN.md:33-34,142; unica/router/migrations/ 中无回滚文件 -->

**从早于本版本的版本升级时，另须注意以下几点：**

1. gateway 与 router 必须同批升级、同批回滚。本版本把坐席在 Chatwoot 点"解决"产生的关闭事件，从出站流改投转人工流，由 router 关闭会话（缺陷 D2 的修复）。只升级 gateway 时，旧 router 会把关闭事件当转人工事件处理并失败，会话不关闭；只升级 router 时，旧 gateway 按嵌套结构读取"解决"回调，识别不了 Chatwoot 的真实回调，会话不会关闭。另外，早于本版本的坐席回复从未送达客户（回调鉴权、报文解析、收件人三处问题，附录 D.5），也要靠这次升级修正。<!-- 依据: doc/known-defects.md:73-81; unica/gateway/internal/webhook/chatwoot.go:430-491; unica/router/internal/handoff/consumer.go:199-206,223-269 -->
2. 行为变化：坐席点"解决"后会话立即关闭，客户再发消息由 AI 重新接待，而不是像旧版本那样留在人工、直到空闲超时。只关闭正由坐席处理的会话：会话此前已因静默自动结束、客户又回到 AI 接待时，事后在 Chatwoot 点"解决"不会打断 AI 接待。转人工时同步到工作台的历史记录（AI 答复、早先的坐席回复）改为内部备注显示。请提前告知坐席。<!-- 依据: doc/known-defects.md:82-83; unica/router/internal/handoff/consumer.go:223-269; unica/router/internal/handoff/history_sync.go:101-139 -->
3. 检查出站流中是否有遗留的关闭事件。旧 gateway 识别不了 Chatwoot 的真实"解决"回调，正常情况下不会留下这类事件；曾用旧报文格式（例如模拟回调）测试过的环境可能留有。旧 gateway 写进出站流的关闭事件没有去重键，发送失败后不会被确认，新 gateway 会定期重新认领并再次写入死信，直到清理为止。执行位置：能访问 Redis 的运维机。
   ```bash
   # 列出未确认的条目（条目 ID、消费者、空闲毫秒数、投递次数），最多 100 条
   redis-cli -u "$REDIS_URL" XPENDING unica:outbound gateway-outbound - + 100
   # 逐条查看内容；字段 type 为 event.conversation_closed 的就是遗留的关闭事件
   redis-cli -u "$REDIS_URL" XRANGE unica:outbound <条目ID> <条目ID>
   # 只对确认为关闭事件的条目执行确认消费
   redis-cli -u "$REDIS_URL" XACK unica:outbound gateway-outbound <条目ID>
   ```
   不要确认其它类型的条目：那是尚未发出的客户答复，故障排除后会被自动重新认领并发送。【待核实-32：现场遗留关闭事件的数量与清理结果】<!-- 依据: unica/gateway/internal/dedup/dedup.go:54-64; unica/gateway/internal/dedup/retry.go:70-78; unica/gateway/internal/stream/consumer.go:128-150,189-193; unica/gateway/internal/stream/producer.go:21,25 -->
4. 升级前已转人工、仍由坐席处理的会话，其 Chatwoot 会话上没有客户的平台用户 ID。gateway 设置了 `DATABASE_URL` 时会从业务库补齐；没有设置时，这些会话里的坐席回复不会发出，gateway 日志为 `cannot be addressed`（6.4）。升级前请为 gateway 配置 `DATABASE_URL`，或在升级前结束这些会话。<!-- 依据: unica/gateway/internal/webhook/chatwoot.go:520-565 -->
5. 回调地址须改为带令牌的写法（2.6 第 10 步）：已开户产品线的收件箱回调地址，以及用初始化脚本配置过的账户级回调地址，须在 Chatwoot 中逐个修改。【待核实-33：现场已开户产品线的收件箱回调地址修改结果】

Dify 与 Chatwoot 的版本在清单中是固定的。仓内只在 Dify 0.15.3 上验证过对接接口，接口形态会随 Dify 版本变化。升级 Dify 前须由乙方回归验证。<!-- 依据: doc/unverified.md:159-162; deploy/dify-preview/README.md:3 -->

### 4.3 告警规则逐条说明

告警规则定义在 `deploy/monitoring/alert-rules.yaml`，共 9 条。告警经 Alertmanager 按级别分组后发给 webhook-adapter：critical 每 1 小时重复一次，warning 每 4 小时重复一次。同名告警中，critical 会抑制 warning。<!-- 依据: deploy/monitoring/alert-rules.yaml:1-162; deploy/monitoring/prometheus-values.yaml:137-171 -->

规则注释中的看板链接写的是 `grafana.unica.local`，现场须替换为实际 Grafana 地址。<!-- 依据: deploy/monitoring/alert-rules.yaml:29,44,60,75,90,105,126,144,161 -->

**① ChannelHighErrorRate（critical）**
- 规则：某渠道出站错误率连续 5 分钟高于 5%。
- 现状：**不会触发**。规则引用的 `gateway_outbound_errors_total` 在代码中不存在，`gateway_outbound_total` 也没有 `channel` 标签。<!-- 依据: deploy/monitoring/alert-rules.yaml:17-30; unica/gateway/internal/metrics/metrics.go:16-20; 全仓搜索 "outbound_errors" 无定义 -->
- 替代观察：死信增长（规则 ⑤）与 gateway 日志 `retry attempt N/3 failed`、`moved to dead-letter`。<!-- 依据: unica/gateway/internal/dedup/retry.go:56-77 -->
- 处置：按 6.1 的"客户收不到回复"排查。

**② QueueBacklog（warning）**
- 规则：`gateway_stream_depth` 连续 5 分钟大于 1000。
- 现状：**不会触发**。该指标已定义，但代码中从未赋值。看板 queue-backlog 中依赖它的面板也为空。<!-- 依据: deploy/monitoring/alert-rules.yaml:33-45; unica/gateway/internal/metrics/metrics.go:36-40; 全仓搜索 "StreamDepth" 无赋值 -->
- 替代观察：3.6 的 `XINFO GROUPS` 命令，看 `pending` 与 `lag`。
- 处置：确认 router 存活且日志无大量错误；确认 Dify 是否变慢（规则 ③）。处理能力不足时可调大 `ROUTER_WORKERS`（默认 4）后重启 router。多副本 router 未经测试，不建议直接加副本。<!-- 依据: unica/router/cmd/router/main.go:350-354; doc/unverified.md:76-78 -->

**③ DifySlowResponse（warning）**
- 规则：Dify 调用耗时的 P95 连续 5 分钟大于 3 秒。这是告警阈值，不是性能承诺。
- 处置：查看 Dify api、worker 的 Pod 状态与日志；检查大模型服务接口自身的响应情况；检查 Dify 容器资源限制。<!-- 依据: deploy/monitoring/alert-rules.yaml:48-61; unica/router/internal/routing/router.go:863-869; deploy/dify/dify-api.yaml:181-186 -->

**④ ServiceDown（critical）**
- 规则：任一采集目标连续 1 分钟不可达（`up == 0`）。
- 前提：UNICA 服务须被 Prometheus 采集到（见 4.4 第 4 条）。
- 处置：查看对应进程或 Pod 是否在运行；查看启动日志中的退出原因（6.7）；排除后重启。

**⑤ DeadLetterGrowing（warning）**
- 规则：1 小时内新增死信超过 10 条。
- 死信来源：gateway 出站发送重试耗尽的消息；本版本起，router 处理转人工事件或坐席"解决"事件失败时，也会把原事件写入死信流，条目带字段 `source=router:unica:handoff`（该字段只在 redis-cli 的输出里可见；用死信查询接口看时，`channel_id` 为空、原消息是转人工事件 JSON 的条目就是 router 写的）。本告警只统计 gateway 的计数器，router 写入的条目不计入；转人工失败看指标 `router_handoff_errors_total`（6.3）。<!-- 依据: deploy/monitoring/alert-rules.yaml:79-80; unica/gateway/internal/dedup/deadletter.go:81; unica/router/internal/handoff/consumer.go:199-220,271-294; unica/gateway/internal/dedup/deadletter.go:21-31 -->
- 旧版本中，按旧报文格式（例如模拟回调）测试时，坐席把会话标为"已解决"会产生死信（失败原因含 `no adapter registered for channel`，原消息类型为 `event.conversation_closed`，已登记缺陷 D2）；真实 Chatwoot 的回调旧版本识别不到，会话只是不关闭。本版本改由 router 关闭会话（代码已修，已按 Chatwoot v3.15.0 源码构造的回调报文测试，待实机验证）；会话已不在坐席处理中时，"解决"事件直接忽略、不进死信。不应再新增这类死信；若仍出现，先按 3.3 第 3 点检查出站流中是否有遗留的关闭事件，再核对 gateway 版本。<!-- 依据: doc/known-defects.md:71-90; unica/gateway/internal/webhook/chatwoot.go:430-491 -->
- 处置：用下面的命令查看最近的死信，按失败原因分类：出站发送失败按 6.1 排查，`source=router:unica:handoff` 的条目按 6.3 排查。
  执行位置：能访问 gateway 内网地址或 Redis 的运维机。
  ```bash
  curl -s "http://【待填：gateway 内网地址】:8080/api/v1/gateway/dead-letter?limit=20"
  redis-cli -u "$REDIS_URL" XREVRANGE unica:dead-letter + - COUNT 20
  ```
  <!-- 依据: unica/gateway/internal/dedup/handler.go:27-75; unica/gateway/internal/dedup/deadletter.go:21-31 -->
- 死信只用于排查。仓内没有死信重放工具。【待核实-24：死信消息的重放方式】

**⑥ NoAvailableAgents（warning）**
- 规则：某产品线 `agent_pool_available` 连续 5 分钟为 0。
- 现状：**按代码推断不会有效触发**。该值只在坐席自动分配成功时更新；而坐席"在线"状态（Redis 键 `agent:status:`）在仓内没有任何写入方，`agents` 表也没有写入接口，自动分配不会成功。【待核实-31：坐席自动分配是否在现场以其他方式启用】<!-- 依据: deploy/monitoring/alert-rules.yaml:94-106; unica/router/internal/scheduling/distributor.go:60-100; unica/router/internal/scheduling/agent_pool.go:18,56-63,139-160; 全仓搜索 "SetOnline(" 与 "INSERT INTO agents" 无业务调用 -->

**⑦ OntologyBreakerTripped（critical）**
- 规则：10 分钟内某产品线的本体熔断被触发。
- 含义：该产品线的本体校验在近期拦截比例过高，熔断器自动停止拦截。熔断打开期间，与本体冲突的答复会发给客户。熔断参数（拦截比例 0.25、最少样本 20、窗口 100、冷却 15 分钟）没有真实流量支撑。<!-- 依据: deploy/monitoring/alert-rules.yaml:115-127; README.zh-CN.md:23,136; doc/unverified.md:64-71 -->

**⑧ ClaimViolationSpike（warning）**

**⑨ TokenRefreshExhausted（critical）**
- 规则：15 分钟内某渠道令牌刷新重试全部失败。
- 含义：该渠道凭证已不可用，消息收发中断。
- 处置：到对应开放平台核对 AppKey / AppSecret 是否过期或被吊销；查看失败详情：

## 6 故障排查

### 6.0 通用排查流程

1. 做 4.1 的健康检查，确认哪个组件不健康。
2. 看 Grafana 告警与看板，判断影响面：单个渠道、单个产品线，还是全局。
3. 按下表的日志关键字搜索对应服务的日志（3.5）。
4. 用 3.6 的命令看 Redis 消息流是否积压。
5. 仍无法定位时，按 8.3 收集信息报障。

### 6.1 渠道收不到消息 / 客户收不到回复

**现象 A：客户发了消息，gateway 日志里没有任何记录。**

检查：
1. 开放平台侧配置的回调地址是否正确，HTTPS 证书是否有效，反向代理是否把 `/webhook/...` 转到 gateway。查看反向代理访问日志里是否有对应的 POST 请求。
2. gateway 启动日志里是否有该渠道的 `adapter registered at /webhook/...`。微信、淘宝、快手只有在 `WECHAT_APP_ID`、`TAOBAO_APP_KEY`、`KUAISHOU_APP_KEY` 非空时才注册，否则回调路径返回 404。<!-- 依据: unica/gateway/cmd/gateway/main.go:129-204 -->
3. 小红书：gateway 须设置 `DATABASE_URL` 与 `AES_ENCRYPTION_KEY`，且门户中该渠道为启用状态；启动日志应有 `dynamic channel config pipeline enabled` 与 `loaded N dynamic channel config(s)`。<!-- 依据: unica/gateway/cmd/gateway/main.go:206-213,354,364 -->
4. 抖音：网关未接入，无法收消息（附录 D）。

处置：修正平台回调配置或 gateway 环境变量，重启 gateway。

**现象 B：gateway 日志有验签失败。**

检查：微信的 `WECHAT_TOKEN`、`WECHAT_ENCODING_AES_KEY`、`WECHAT_ENCRYPTED_MODE` 是否与公众平台设置一致；淘宝、快手的 AppSecret、回调密钥是否与开放平台一致。<!-- 依据: unica/gateway/internal/config/config.go:73-88; unica/gateway/internal/adapter/wechat/handler.go:37-58 -->

处置：改为一致后重启 gateway。

**现象 C：gateway 有 `message published`，但客户收不到 AI 答复。**

检查：
1. router 日志是否有 `failed to resolve route for channel <ID>`。有则说明渠道 ID 不在 `channels` / `channel_configs` 中、未启用，或不是 UUID（2.6 第 9 步）。用 6.0 的 SQL 对照渠道 ID。
2. `XINFO GROUPS unica:inbound` 中 `router-group` 的 `pending` 或 `lag` 是否持续增长。增长说明 router 没在消费：检查 router 是否存活、日志是否有 `XREADGROUP error`。<!-- 依据: unica/router/internal/routing/router.go:295 -->
3. router 日志是否有分区错误（6.9）。
4. 该客户的会话是否处于 `human_processing`。这种状态下消息转给 Chatwoot，AI 不回复，属于正常行为。
5. 以上都正常，转 6.2。

**现象 D：router 有 `AI response published`，客户仍收不到。**

检查：
1. gateway 日志是否有 `[dedup] retry attempt N/3 failed` 或 `moved to dead-letter`，看错误内容（凭证、平台接口错误、网络）。
2. 是否有 `no adapter registered for channel <ID>`：gateway 没有这个渠道的发送器（环境变量缺失，或小红书配置未加载）。
3. 是否有令牌刷新失败（4.3 ⑨）。
4. 查看死信（4.3 ⑤）。

处置：修正凭证或配置后重启 gateway。已进入死信的消息不会自动重发。【待核实-24】

### 6.2 AI 不回复或回复为空

检查：
1. router 日志：
   - `Dify API error`：调用 Dify 失败（网络、Dify 故障、应用 Key 无效）。系统已改为转人工，原因记为 `ai_unavailable`。
   - `Dify returned empty answer` 或 `empty answer withheld`：Dify 返回空答复，系统不把空白发给客户，已改为转人工。<!-- 依据: unica/router/internal/routing/router.go:858-895,970-978 -->
   - `message has no text content for AI`：客户发的是非文字消息，不调用 AI。<!-- 依据: unica/router/internal/routing/router.go:556-562 -->
2. 指标 `router_dify_errors_total` 的 `error_type`：`api_call` 或 `empty_answer`。
3. Dify 的 api、worker、nginx 是否在运行；Dify api 日志有无报错。
4. Dify 控制台中大模型服务的配置、密钥、额度是否正常（大模型服务由甲方开通）。
5. 用 6.0 的 SQL 确认该产品线 `dify_base_url` 可达、`has_dify_key` 为 true。
6. 频繁空答复：可能是生成长度上限过小，答复在输出前被截断（已登记缺陷 D18）。在门户平台管理页的模型清单中检查各产品线的生成长度参数（接口 `GET /api/v1/platform/models`），由乙方调整。<!-- 依据: doc/known-defects.md:615-672; unica/admin/cmd/admin/main.go:603-619 -->
7. AI 有回复但频繁转人工：用 6.0 的 SQL 看转人工原因分布。`low_confidence` 偏多时，转 6.6 检查知识库；阈值在门户 AI 设置中调整。<!-- 依据: unica/admin/cmd/admin/main.go:723-731; unica/pkg/guardrail/evaluator.go:46 -->

处置：恢复 Dify 或大模型服务；修正产品线绑定；必要时由乙方调整模型参数。

### 6.3 转人工失败

现象：客户要求转人工，或系统判定转人工后，Chatwoot 里看不到这个会话。

检查：
1. router 日志是否有 `handoff event published for conversation <会话ID>`。若是 `failed to publish handoff event`，说明写 Redis 失败，检查 Redis。<!-- 依据: unica/router/internal/routing/router.go:1424-1441 -->
2. router 日志是否有 `[handoff] failed to handle event ... (conv=<会话ID>)`，按错误内容判断：
   - 含 `incomplete chatwoot config` 或 `has no config_json`：该产品线没有绑定 Chatwoot。开户时未配置 `CHATWOOT_BASE_URL` / `CHATWOOT_PLATFORM_TOKEN`，或 Chatwoot 步骤失败。
   - 含 `find/create chatwoot contact` 或 `find/create chatwoot conversation`：Chatwoot 不可达，或产品线保存的 Chatwoot API Token 无效。查看 Chatwoot web 日志。
   - 含 `get conversation`、`get messages`：数据库问题。
   - 含 `create contact response carries no contact id`：Chatwoot 新建联系人的返回格式与本系统适配的 v3.15.0 不同，先核对 Chatwoot 版本。
   <!-- 依据: unica/router/internal/handoff/handler.go:89-133,389-428; unica/router/internal/handoff/consumer.go:209-220 -->
3. 指标 `router_handoff_errors_total` 的 `error_type`。
4. 查看产品线的 Chatwoot 绑定（不显示令牌本身）：
   ```sql
   SELECT name,
          config_json->'chatwoot'->>'base_url'   AS cw_base_url,
          config_json->'chatwoot'->>'account_id' AS cw_account,
          config_json->'chatwoot'->>'inbox_id'   AS cw_inbox,
          coalesce(config_json->'chatwoot'->>'api_token', '') <> '' AS has_cw_token
   FROM product_lines ORDER BY name;
   ```
   <!-- 依据: unica/router/internal/bridge/chatwoot.go:19-25; unica/router/internal/handoff/handler.go:400-421 -->
5. Chatwoot 里有会话但没人接：UNICA 的自动分配坐席不生效（4.3 ⑥），坐席须在 Chatwoot 的未分配列表中领取。
6. 日志 `[handoff] summary generation failed, using fallback` 只表示摘要改用简版，不影响转人工。<!-- 依据: unica/router/internal/handoff/handler.go:305-313 -->
7. 每次转人工都会有一行 `[handoff] warning: state transition to human_processing failed ... from "human_processing" to "human_processing"`，属正常：router 发出转人工事件后已先把会话转为人工处理。<!-- 依据: unica/router/internal/routing/router.go:1162-1166; unica/router/internal/handoff/handler.go:183-188 -->

处置：
- 补全产品线的 Chatwoot 绑定：由管理员对该租户重新提交开户（开户各步骤幂等，会补做缺失的步骤）。开户中的 Chatwoot 步骤已在本地 Chatwoot v3.15.0 实例上验证（附录 D.6），对现场实例【待核实-11】。<!-- 依据: README.zh-CN.md:25,135; doc/unverified.md:127-134 -->
- 转人工事件处理失败后**不会重试**，事件已被确认消费，但原事件会在死信流 `unica:dead-letter` 留一份（4.3 ⑤）。须从死信、日志或 `handoff_events` 表找出受影响的会话，通知坐席跟进。router 在发出转人工事件后，已把会话置为 `human_processing`。绑定补全之前，客户的后续消息转发到 Chatwoot 也会失败（router 日志 `failed to forward to Chatwoot`），直到会话因空闲超时关闭；绑定补全后，客户的下一条消息会由 router 转发到 Chatwoot，转发时按需创建 Chatwoot 会话。早于 `92ea9ae` 的版本解析不了 Chatwoot 新建联系人的返回，每位新客户的第一次转人工都会失败并进入死信（附录 D.6）；升级后应在死信流中查 `source` 为 `router:unica:handoff` 的条目，找出受影响的会话。<!-- 依据: unica/router/internal/bridge/chatwoot.go:216-262; unica/router/internal/handoff/consumer.go:209-220,271-294; unica/router/internal/routing/router.go:1031-1035,1053-1059,448-455; unica/router/internal/routing/chatwoot_forwarder.go:47-124; unica/router/cmd/router/main.go:362-366 -->

### 6.4 坐席在 Chatwoot 回复了，客户收不到

检查：
1. gateway 启动日志是否有 `Chatwoot webhook handler registered at /api/v1/webhook/chatwoot`。没有则说明 `CHATWOOT_WEBHOOK_TOKEN` 未设置，回调路径不存在。<!-- 依据: unica/gateway/cmd/gateway/main.go:101-124 -->
2. gateway 日志是否有 `invalid webhook token received`：Chatwoot 收件箱（或账户级回调）的地址没有带 `?token=`，或令牌与 `CHATWOOT_WEBHOOK_TOKEN` 不一致（2.6 第 10 步）。<!-- 依据: unica/gateway/internal/webhook/chatwoot.go:238-253 -->
3. Chatwoot 收件箱配置的回调地址，是否为带令牌的 `CHATWOOT_WEBHOOK_URL`，且 Chatwoot 能访问到。
4. gateway 日志是否有 `carries no unica_conversation_id`：这个 Chatwoot 会话不是 UNICA 建的（例如在 Chatwoot 中手工新建、来自网站挂件或邮箱收件箱），或者它的 `unica_conversation_id` 属性被删除了。该条回复不会发出，坐席须通过其它方式联系客户。<!-- 依据: unica/gateway/internal/webhook/chatwoot.go:493-511 -->
5. gateway 日志是否有 `cannot be addressed`：找不到客户的平台用户 ID 或渠道（升级前建的会话，且 gateway 没有设置 `DATABASE_URL`）。按 3.3 第 4 点处理。日志为 `of account … refused` 或 `which does not exist` 时，回调来自的 Chatwoot 账户与会话所属产品线不一致，或会话不存在，回复被拒绝；检查是否有人改动了该会话的自定义属性。<!-- 依据: unica/gateway/internal/webhook/chatwoot.go:520-565 -->
6. 日志 `skipping private message`：坐席用的是"私有备注"，不会发给客户，属正常。<!-- 依据: unica/gateway/internal/webhook/chatwoot.go:310-313 -->
7. 日志 `already forwarded, duplicate delivery skipped`：同一条回复被两处回调各推送了一次，第二次被忽略，属正常。<!-- 依据: unica/gateway/internal/webhook/chatwoot.go:336-340 -->
8. 有 `agent reply published to outbound stream` 后客户仍收不到：按 6.1 现象 D 检查出站发送。<!-- 依据: unica/gateway/internal/webhook/chatwoot.go:386-387 -->
9. 指标 `chatwoot_webhook_errors_total`。

处置：修正令牌或回调地址后重启 gateway。无法找到会话或收件人的回复不会补发，只能人工联系客户。

### 6.5 门户登录失败

检查（在浏览器开发者工具中看 `/api/v1/auth/login` 的返回）：

| 返回 | 原因 | 处置 |
|---|---|---|
| 502 / 504 或无响应 | nginx 反代到 admin 不通 | 检查 admin 进程、端口、反代地址 |
| 401 `invalid credentials` | 账号或密码错误 | 核对账号；见下方"重置密码" |
| 401 `account is deactivated` | 账号已停用 | 管理员重新启用（接口 `PUT /api/v1/users/{id}` 的 `is_active` 字段） |
| 500 `internal error` | admin 查询数据库失败，日志有 `[auth] login lookup error` | 检查数据库连接（2.4 的账号要求） |
| 500 `failed to generate tokens` | 签发令牌失败 | 查看 admin 日志 |

<!-- 依据: unica/admin/internal/handler/auth.go:43-92 -->

其它情况：
- 登录后不久提示 `refresh token revoked or expired`：续期令牌存于 Redis，有效期 7 天。Redis 数据丢失或被淘汰时会出现。重新登录即可。<!-- 依据: unica/admin/internal/handler/auth.go:118-131; unica/admin/internal/config/config.go:73-74 -->
- 所有人同时被要求重新登录：`JWT_SECRET` 发生了变化（例如重启时取值不同）。重新登录即可，并确认该值固定保存。
- 访问令牌有效期 2 小时，续期令牌 7 天，属正常设计。<!-- 依据: unica/admin/internal/config/config.go:73-74 -->

**重置密码。** 门户与管理接口都没有修改密码的功能（数据层的方法存在但没有接口调用它）。忘记密码时，只能由乙方或在乙方指导下，用新的 bcrypt 哈希更新 `users.password_hash`。【待核实-06】<!-- 依据: unica/admin/internal/identity/users.go:30-45,225-245; unica/admin/internal/repository/user.go:155-160 -->

### 6.6 知识库检索为空 / 知识库管理不可用

**现象 1：门户知识库页提示不可用，接口返回 503。** 返回内容为 `knowledge base management is unavailable: DIFY_DATASET_API_KEY is not configured for this service`。admin 启动日志有 `DIFY_DATASET_API_KEY not set`。处置：按 2.6 第 2 步生成数据集 Key，设置后重启 admin。<!-- 依据: unica/admin/internal/tenant/knowledge/knowledge.go:236-240; unica/admin/cmd/admin/main.go:271-273 -->

**现象 2：上传文件失败。**
- 返回 413：文件超过 15MB，或门户反向代理的请求体上限过小（2.6 第 7 步）。Dify 自带的 nginx 上限为 15M。<!-- 依据: unica/admin/internal/tenant/knowledge/knowledge.go:40; deploy/dify/dify-nginx.yaml:35 -->
- Dify 拒绝上传，错误含 `provider_not_initialize`：平台索引方式为 `high_quality`，但 Dify 工作区没有配置文本嵌入模型。处置：在 Dify 中配置嵌入模型（可使用本地嵌入服务，`deploy/embeddings/README.md`）。不建议为绕过报错而改成 `economy`（见现象 3）。<!-- 依据: doc/known-defects.md:283-324; unica/admin/internal/config/config.go:29-43 -->

**现象 3：上传成功、索引完成，但 AI 用不上知识库内容，或检索恒为空。** 这类问题不会报错。

检查：
1. 门户平台管理页的知识库清单（接口 `GET /api/v1/platform/knowledge`）。它逐条线检查应用、数据集、挂载、检索设置是否就位，挂载与检索是实时向 Dify 查询的。<!-- 依据: unica/admin/cmd/admin/main.go:621-638; doc/known-defects.md:185-192 -->
2. 显示"未挂载"或缺数据集：用门户诊断卡上的修复按钮，或管理员调用 `POST /api/v1/tenants/{id}/ai-settings/knowledge/provision`（幂等）。<!-- 依据: doc/known-defects.md:218-219; unica/admin/cmd/admin/main.go:734-744 -->
3. 索引方式为 `economy` 而检索方式为 `semantic_search`：检索恒为空且不报错（已登记 D24）。清单会把这种库标红。处置：在 Dify 控制台把该库检索方式改为 `keyword_search`，或重建索引。<!-- 依据: doc/known-defects.md:815-836 -->

6. router 日志 `RAG source N for conversation ...: dataset=... doc=... score=...` 显示每次检索到的文档；指标 `router_dify_retrieval_hit_total` / `router_dify_retrieval_miss_total` 显示命中情况。<!-- 依据: unica/router/internal/routing/router.go:943; unica/router/internal/metrics/metrics.go:68-78 -->

### 6.10 Redis 内存与消息积压

背景：
- 清单中 Redis 设置 `maxmemory 512mb`、`maxmemory-policy allkeys-lru`。内存满时 Redis 会淘汰任意键，包括消息流、会话映射、续期令牌。<!-- 依据: deploy/redis/values.yaml:28-30 -->
- UNICA 的消息流不做裁剪，会持续增长（1.6）。
- 按仓内清单，Dify 与 Chatwoot 也使用同一个 Redis 实例（分别为 0 号与 1 号库），UNICA 默认也使用 0 号库。<!-- 依据: deploy/dify/dify-secrets.yaml:24; deploy/dify/dify-api.yaml:94-95; deploy/chatwoot/chatwoot-secrets.yaml:23; unica/gateway/internal/config/config.go:62 -->

检查（执行位置：能访问 Redis 的运维机）：

```bash
redis-cli -u "$REDIS_URL" INFO memory | grep -E 'used_memory_human|maxmemory_human|maxmemory_policy'
redis-cli -u "$REDIS_URL" INFO stats  | grep evicted_keys
redis-cli -u "$REDIS_URL" XLEN unica:inbound
redis-cli -u "$REDIS_URL" XLEN unica:outbound
redis-cli -u "$REDIS_URL" XLEN unica:handoff
redis-cli -u "$REDIS_URL" XLEN unica:dead-letter
```

### 7.3 密钥轮换

| 密钥 | 步骤 | 影响 |
|---|---|---|
| `JWT_SECRET` | 修改 admin 环境变量 → 重启 admin | 所有用户需重新登录 |
| 业务库口令 | 在 PostgreSQL 修改该账号口令 → 同步更新 router 的 `POSTGRES_URL`，admin、reporter、gateway 的 `DATABASE_URL`，以及 Secret `unica-db-credentials` → 重启这些服务 | 重启期间对话中断 |
| Dify / Chatwoot 数据库口令 | 修改对应数据库账号口令 → 更新 `dify-secrets` 或 `chatwoot-secrets` → 重启 Dify 或 Chatwoot | 对应组件短暂不可用 |
| Redis 口令 | 修改 Redis 口令 → 更新所有 `REDIS_URL`、`dify-secrets` 的 `REDIS_PASSWORD`、`chatwoot-secrets` 的 `REDIS_URL` → 重启全部相关服务 | 全局短暂中断 |
| `CHATWOOT_WEBHOOK_TOKEN` | 同时修改 gateway 变量、admin 的 `CHATWOOT_WEBHOOK_URL` 与 Chatwoot 中各收件箱（及账户级）回调地址里的 `token` 参数 → 重启 gateway 与 admin | 修改期间坐席回复无法回到客户 |

| `DIFY_DATASET_API_KEY` | 在 Dify 新建 → 更新 admin → 重启 admin → 删除旧 Key | 只影响知识库管理 |
| `DIFY_ADMIN_PASSWORD` | 修改 Dify 管理员密码 → 更新 admin → 重启 admin | 只影响开户与推送 |
| 渠道凭证（AppSecret 等） | 开放平台侧重置 → 微信/淘宝/快手改 gateway 变量并重启；小红书在门户渠道页更新 | 修改期间该渠道中断 |
