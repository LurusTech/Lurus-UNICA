## 1. Executive Summary

UNICA is a self-hosted, multi-channel AI customer service hub that unifies five major platforms (WeChat, Douyin, Xiaohongshu, Taobao, Kuaishou) into a single intelligent service system. The system leverages AI to automatically handle 70%+ of customer inquiries while enabling seamless human handoff for complex cases, supporting 7-8 independent product lines with full data isolation.

### 1.1 Business Objectives

1. **Unify channels** - Consolidate 5 platform backends into a single agent workspace, eliminating context-switching overhead
2. **AI automation** - Achieve 70%+ AI-resolved inquiries, reducing human labor costs and enabling 24/7 coverage
3. **Boost conversion** - Leverage AI proactive engagement to increase customer acquisition conversion rate by 20%+

### 1.2 Success Metrics

| Metric | Target | Measurement |
|--------|--------|-------------|
| AI Auto-Resolution Rate | >= 70% | Conversations resolved by AI without human handoff |
| First Response Time | < 3s | Time from user message to AI reply |
| Human Takeover Response | < 30s | Time from AI handoff to first human reply |
| Customer Satisfaction | >= 4.5/5 | Post-conversation user rating |
| Acquisition Conversion | +20% | AI-driven inquiry-to-lead conversion lift |

## 2. User Personas

### Persona 1: Frontline Agent (20+ users)
- **Role:** Handles customer inquiries across product lines
- **Tech Level:** Basic, needs intuitive UI
- **Goals:** Quick access to conversation context, reduce repetitive work
- **Pain Points:** Platform switching, repetitive FAQ answers

### Persona 2: Team Supervisor
- **Role:** Monitors team performance, manages scheduling
- **Goals:** Real-time visibility into team metrics, quality control
- **Pain Points:** No unified dashboard across platforms

### Persona 3: Knowledge Admin / Operations
- **Role:** Maintains AI knowledge base content per product line
- **Goals:** Easy document management, prompt tuning
- **Pain Points:** Knowledge scattered across platforms

### Persona 4: System Administrator
- **Role:** Manages channel configurations, permissions, system health
- **Goals:** Reliable system operation, easy channel onboarding
- **Pain Points:** Complex multi-platform credential management

## 3. Functional Requirements

### 3.1 Multi-Channel Gateway

#### FR-001: Multi-Channel Message Reception
**Priority:** Must Have
**Description:** Support message reception from WeChat (Official Account / Video Account), Douyin, Xiaohongshu, Taobao, and Kuaishou, including signature verification and encryption/decryption per platform specification.
**Acceptance Criteria:**
- [ ] Messages received from all 5 channels within platform SLA
- [ ] Signature verification passes for each platform
- [ ] Encryption/decryption handles all message types per platform
- [ ] Failed verification returns appropriate error response

#### FR-002: Unified Message Format
**Priority:** Must Have
**Description:** Transform heterogeneous platform messages into a system-standard JSON format, normalizing text, image, video, and link message types.
**Acceptance Criteria:**
- [ ] Standard JSON schema defined and documented
- [ ] All 5 platform message formats correctly mapped
- [ ] Text, image, video, link types supported
- [ ] Original platform metadata preserved for reply routing

#### FR-003: Message Deduplication & Retry
**Priority:** Must Have
**Description:** Ensure idempotent message processing with timeout-based retry and dead-letter queue for persistent failures.
**Acceptance Criteria:**
- [ ] Duplicate messages detected and discarded (idempotency key)
- [ ] Failed messages retried up to 3 times with exponential backoff
- [ ] Permanently failed messages routed to dead-letter queue
- [ ] Dead-letter queue visible for manual inspection

#### FR-004: Rate Limiting & Anti-Abuse
**Priority:** Should Have
**Description:** Enforce per-channel API call rate limits and block malicious/abnormal request patterns.
**Acceptance Criteria:**
- [ ] Rate limits configurable per channel
- [ ] Exceeding rate limits returns 429 with retry-after header
- [ ] Abnormal request patterns (burst, repeated) detected and throttled

#### FR-005: Token Auto-Management
**Priority:** Must Have
**Description:** Automatically refresh and cache Access Tokens for all platforms, handling token expiration and concurrent refresh scenarios.
**Acceptance Criteria:**
- [ ] Tokens refreshed before expiration (with buffer time)
- [ ] Concurrent refresh requests deduplicated (single-flight)
- [ ] Token cache in Redis with appropriate TTL
- [ ] Token refresh failure triggers alert (FR-024)

### 3.2 Conversation Routing & Management

#### FR-006: Intelligent Conversation Routing
**Priority:** Must Have
**Description:** Automatically identify the product line from incoming messages and route conversations to the corresponding AI Agent.
**Acceptance Criteria:**
- [ ] Product line identified from channel/account mapping
- [ ] New conversations routed to correct AI Agent within 500ms
- [ ] Routing rules configurable per channel-product mapping
- [ ] Unrecognized conversations routed to default handler

#### FR-007: AI-to-Human Handoff
**Priority:** Must Have
**Description:** Automatically transfer to human agent when AI confidence drops below threshold; users can also trigger handoff via keyword or button.
**Acceptance Criteria:**
- [ ] Auto-handoff when confidence < configurable threshold
- [ ] User-initiated handoff via keyword (e.g., "transfer to human")
- [ ] Handoff queues prioritized by wait time
- [ ] Handoff notification sent to available agents

#### FR-008: Human Takeover Context
**Priority:** Must Have
**Description:** When transferring to human agent, carry complete AI conversation history and an intent summary so agents can continue without asking users to repeat.
**Acceptance Criteria:**
- [ ] Full AI conversation history visible to human agent
- [ ] AI-generated intent summary displayed at top
- [ ] Customer sentiment indicator included
- [ ] Agent can view original platform message format if needed

#### FR-009: Conversation State Management
**Priority:** Must Have
**Description:** Track conversation lifecycle states: Pending → AI Processing → Human Processing → Closed, with automatic timeout closure.
**Acceptance Criteria:**
- [ ] State transitions enforced (no invalid jumps)
- [ ] Idle conversations auto-closed after configurable timeout
- [ ] State changes logged with timestamps
- [ ] Real-time state visible in agent workspace

#### FR-010: Agent Scheduling & Distribution
**Priority:** Should Have
**Description:** Distribute conversations to human agents based on product line assignment, skill set, online status, and current load.
**Acceptance Criteria:**
- [ ] Agents assigned to product lines with skill tags
- [ ] Round-robin or least-load distribution within a team
- [ ] Offline agents excluded from routing
- [ ] Maximum concurrent conversations configurable per agent

### 3.3 AI Smart Response & Knowledge Base

#### FR-011: Multi-Product Independent Agents
**Priority:** Must Have
**Description:** Each product line has a dedicated AI Agent with isolated system prompt, knowledge base, and conversation context. No cross-contamination between product lines.
**Acceptance Criteria:**
- [ ] Each product line maps to exactly one Dify Agent
- [ ] Agent prompts independently configurable
- [ ] Knowledge base queries scoped to product line
- [ ] Cross-product queries return no results (isolation verified)

#### FR-012: RAG Knowledge Retrieval
**Priority:** Must Have
**Description:** Vector-based retrieval augmented generation (RAG) using pgvector for product knowledge, delivering accurate and contextual answers.
**Acceptance Criteria:**
- [ ] Documents vectorized and stored in pgvector per product line
- [ ] Top-K relevant chunks retrieved for each query
- [ ] Retrieved context included in LLM prompt
- [ ] Answer cites source document when applicable

#### FR-013: Knowledge Base Management
**Priority:** Must Have
**Description:** Support document upload (PDF, Word, TXT, Markdown), automatic vectorization, update, and deletion, with product-line isolation.
**Acceptance Criteria:**
- [ ] Upload supports PDF, DOCX, TXT, MD formats
- [ ] Documents auto-vectorized on upload
- [ ] Update replaces vectors without affecting other documents
- [ ] Delete removes all associated vectors
- [ ] Operations scoped to product line (admin can only manage own line)

#### FR-014: Proactive Marketing Conversations
**Priority:** Should Have
**Description:** AI identifies acquisition intent signals and proactively recommends products, promotions, or follow-up actions.
**Acceptance Criteria:**
- [ ] Intent signals configurable (e.g., price inquiry, comparison)
- [ ] Proactive messages triggered by intent match
- [ ] Marketing templates configurable per product line
- [ ] Conversion events tracked for analytics (FR-022)

#### FR-015: Confidence Scoring & Safety Guardrails
**Priority:** Must Have
**Description:** AI responses include confidence scores. Low-confidence replies trigger auto-handoff or refusal. Sensitive topics (legal, medical claims) blocked.
**Acceptance Criteria:**
- [ ] Each AI response tagged with confidence score
- [ ] Below threshold: auto-handoff to human (links to FR-007)
- [ ] Sensitive topic detection blocks inappropriate responses
- [ ] Guardrail rules configurable per product line

## 4. Non-Functional Requirements

### NFR-001: Performance
**Priority:** Must Have
**Description:** Gateway message processing latency < 100ms (excluding AI inference). AI response time < 3 seconds (including RAG retrieval + LLM generation). System supports 100-1000 QPS with elastic scaling.
**Acceptance Criteria:**
- [ ] P95 gateway latency < 100ms under 500 QPS load
- [ ] P95 AI response time < 3s under normal load
- [ ] System stable at 1000 QPS peak (no message loss)

### NFR-002: Availability
**Priority:** Must Have
**Description:** 99.9% monthly uptime. Single-channel failure isolated from other channels. Rolling upgrades with zero downtime.
**Acceptance Criteria:**
- [ ] Monthly uptime >= 99.9% (< 43.8 min downtime/month)
- [ ] Channel failure does not cascade (circuit breaker pattern)
- [ ] K3s rolling deployment verified with zero-downtime test

### NFR-003: Security
**Priority:** Must Have
**Description:** Sensitive data (phone numbers, addresses) encrypted in transit and masked/encrypted at rest. Full private deployment, no data leaves server.
**Acceptance Criteria:**
- [ ] All external API calls over HTTPS/TLS
- [ ] PII fields encrypted at database level
- [ ] No external data transmission (verified via network audit)
- [ ] Platform API credentials encrypted in config store

### NFR-004: Scalability
**Priority:** Must Have
**Description:** Gateway and AI layers horizontally scalable. New channel onboarding does not require changes to existing services.
**Acceptance Criteria:**
- [ ] Gateway scales by adding pods (stateless design)
- [ ] New channel adapter deployable independently
- [ ] Database connection pooling supports scaled instances

### NFR-005: Maintainability
**Priority:** Should Have
**Description:** Channel adapters independently deployable. Single-channel update does not affect global system. Adapter plugin pattern for new channels.
**Acceptance Criteria:**
- [ ] Each channel adapter is a separate deployable unit
- [ ] Adapter interface/contract documented
- [ ] New channel onboarding requires only adapter implementation

### NFR-006: Observability
**Priority:** Must Have
**Description:** Full-chain log tracing with correlation IDs. Key metrics exposed to visualization dashboard.
**Acceptance Criteria:**
- [ ] Request correlation ID flows from gateway to AI to response
- [ ] Structured logging (JSON) for all services
- [ ] Metrics dashboard with real-time system health view

## 8. Key User Flows

### Flow 1: Customer Inquiry (AI Resolution)
```
Customer sends message on WeChat
  → Gateway receives, verifies, normalizes
  → Router identifies product line, forwards to AI Agent
  → AI retrieves knowledge via RAG, generates response
  → Confidence check passes (above threshold)
  → Response sent back through gateway to WeChat
  → Conversation auto-closed after idle timeout
```

### Flow 2: AI-to-Human Handoff
```
AI confidence drops below threshold
  → System triggers handoff, generates intent summary
  → Conversation queued for human agent (product-line team)
  → Agent receives notification with full context
  → Agent continues conversation in unified workspace
  → Conversation closed, satisfaction survey sent
```

### Flow 3: Knowledge Base Update
```
Knowledge admin uploads new product document
  → Document parsed and vectorized
  → Vectors stored in pgvector (product-line scoped)
  → AI Agent immediately uses updated knowledge
  → Admin verifies via test query
```

## 10. Assumptions

1. All 5 platform APIs support webhook-based message push (verified in platform docs)
2. Chatwoot's custom channel API is sufficient for integration without forking source code
3. Dify's API supports external conversation management and per-agent knowledge base isolation
4. A single PostgreSQL instance with pgvector can handle the knowledge base scale for 7-8 product lines
5. Platform API approval timelines are manageable (1-4 weeks per platform)
6. LLM inference costs are acceptable at the projected conversation volume

## 11. Out of Scope

- Voice/video call support (text-based messaging only for v1)
- Email channel integration
- CRM integration (customer relationship management)
- Payment/order processing within conversations
- Mobile app for agents (web-based workspace only for v1)
- Multi-language support (Chinese only for v1)
- Custom AI model training (using pre-trained LLM via Dify)

## 12. Open Questions

1. **LLM selection** - Which LLM will be used (self-hosted vs. API)? Affects latency, cost, and data privacy.
2. **Chatwoot customization depth** - How much UI customization is needed beyond Chatwoot defaults? May affect timeline.
3. **Platform API approval timeline** - Actual approval times may vary; need contingency plan if delayed.
4. **Knowledge base scale** - How large are the product knowledge bases? Affects vectorization strategy and storage.
5. **Conversation volume projection** - Need actual message volume data per channel for capacity planning.

## 13. Technical Decisions (From Product Brief)

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Gateway Language | Go | High dev efficiency, mature concurrency model, rich ecosystem |
| Agent Workspace | Chatwoot (OSS) | Mature multi-channel platform, reduces frontend effort |
| AI Orchestration | Dify (OSS) | Multi-agent + RAG capabilities, per-product isolation |
| Database | PostgreSQL + pgvector | Unified relational + vector storage, reduces complexity |
| Deployment | K3s containerized | Lightweight K8s, suitable for multi-cloud private deployment |
