UNICA - 跨渠道 AI 客服中枢系统项目简报 (Project Brief)
(Unified Intelligent Customer Assistant)

一、 项目背景与核心目标
本项目旨在打造一套高可用、私有化部署的全渠道 AI 客服接入与管理平台 。系统将无缝对接微信（公众号/视频号）、抖音、小红书、淘宝、快手五大核心渠道 ，抹平各平台协议差异 。核心目标是利用 AI 实现自动化获客与产品咨询解答，同时通过完善的会话路由机制实现人工无缝接管 ，高效支撑 7 至 8 个独立产品线的全天候客服需求。

1.1 现状与痛点
当前客服运营存在两大核心痛点：
- 多平台割裂：客服人员需在微信、抖音、小红书等多个平台后台之间频繁切换，操作效率低下，容易漏回消息。
- 纯人工响应：完全依赖人工回复，大量重复性咨询（产品参数、价格、使用方法等）占用人力资源，人力成本居高不下，且无法实现 7x24 全天候覆盖。

二、 目标用户

2.1 主要用户角色
- 一线客服人员（20+ 人）：分布在 7-8 个产品线，日常通过工作台处理客户咨询，技术水平一般，需要简洁直观的操作界面。
- 客服主管/组长：监控各产品线会话质量、查看数据报表、管理团队排班与权限分配。
- 运营/知识库管理员：维护各产品线的 AI 知识库内容，调优 AI 回复话术和 Prompt。
- 系统管理员：负责渠道接入配置、系统运维与权限管理。

2.2 多团队隔离需求
各产品线客服团队之间需要严格的数据与权限隔离，确保：
- 会话数据不串线（A 产品客服看不到 B 产品的会话）
- AI 知识库按产品线独立维护，互不干扰
- 报表与统计按团队/产品线维度分别呈现

三、 成功指标 (KPI)

| 指标 | 目标值 | 衡量方式 |
|------|--------|----------|
| AI 自动解决率 | >= 70% | AI 独立完成的会话占比（无需转人工） |
| 首次响应时间 | < 3 秒 | 用户发送消息到收到 AI 回复的时间 |
| 人工接管响应时间 | < 30 秒 | AI 转人工后，客服首次回复的时间 |
| 客户满意度 | >= 4.5/5 | 会话结束后的用户评分 |
| 获客转化率 | 提升 20%+ | AI 主动营销带来的咨询转化提升 |

四、 系统架构设计
系统采用“接入层-核心层-数据层”三层微服务架构 ，实现各模块深度解耦 ：


接入层 (多渠道适配网关)： 使用 Go 自研高性能轻量级网关。负责统一接收各渠道 API 消息、加解密处理、验签及频率控制，将复杂异构的外部消息转化为系统标准 JSON 格式 。


中枢层 (统一路由与工作台)： 部署开源 Chatwoot。作为人工与 AI 的调度中心，管理多渠道统一收件箱、分配工单、监控会话状态 ，并执行“转人工”逻辑 。

AI 大脑层 (意图与知识中枢)： 部署开源 Dify。利用其多 Agent 编排能力，为 7-8 个不同的产品建立互相隔离的专属智能体和检索增强生成（RAG）工作流。

数据与基建层：

PostgreSQL (含 pgvector)： 作为核心骨干数据库，统一承载会话历史、业务数据关系映射以及各产品线专属的向量化知识库。


Redis： 负责高频数据缓存、全局会话状态维护、各渠道 Access Token 的自动刷新与防刷限流机制 。


底层部署： 全量服务容器化，依托分布于多云节点的 K3s 集群进行高可用部署和横向动态扩容 。

五、 非功能性需求

5.1 性能要求
- 并发处理能力：100-1000 QPS，日均消息量数万条，需支持高峰期弹性扩容
- 网关消息处理延迟：< 100ms（不含 AI 推理时间）
- AI 推理响应：< 3 秒（含 RAG 检索 + LLM 生成）

5.2 可用性
- 系统整体可用性目标：99.9%（月度）
- 单渠道故障不影响其他渠道正常运行（故障隔离）
- 支持滚动升级，业务不中断

5.3 数据安全与合规
- 遵守各接入平台的数据使用规范与隐私政策
- 用户敏感信息（手机号、地址等）传输加密、存储脱敏
- 私有化部署，数据不出服务器

六、 核心交付物

标准化跨渠道网关： 具备高可用容错机制、支持消息去重与超时重试的 Go 独立微服务模块 。

多产品 AI 知识基座： 基于产品的独立向量知识库矩阵，确保解答精确度，不串档、不混淆。


全渠道人工协同工作台： 支持历史对话记录无缝同步、快捷话术调用的可视化客服后台 。

七、 风险与依赖

| 风险项 | 影响 | 缓解措施 |
|--------|------|----------|
| 各平台 API 权限审批周期不可控 | 阻塞渠道接入开发 | 优先申请微信/抖音，其余渠道并行推进；开发期使用 Mock 接口 |
| Chatwoot/Dify 定制边界 | 深度定制可能需 fork 维护 | 优先使用 API/Webhook 集成，避免侵入式修改源码 |
| 各平台 API 协议变更 | 网关适配层需频繁更新 | 网关采用适配器模式，单渠道变更不影响整体 |
| AI 幻觉/错误回复 | 影响客户体验与品牌形象 | 设置置信度阈值，低于阈值自动转人工；关键场景强制人工审核 |

当前依赖状态：
- 各平台开发者账号：尚未申请（阶段 1 首要任务）

八、 阶段性实施计划
参照风险控制最佳实践，项目分五个核心阶段敏捷推进 ：


阶段 1：需求架构与权限筹备 (1-2周) 

确立数据库表结构设计与 API 字段规范 。

在各平台（微信、抖音、小红书等）注册开发者账号、创建应用并申请消息推送、订单查询等关键 API 权限 。


阶段 2：自研网关与基建搭建 (4-6周) 

在 K3s 集群中拉起 PostgreSQL 与 Redis 实例 。

使用 Go 优先完成 1-2 个高优渠道（如微信、抖音）的适配网关开发与联调 。


阶段 3：中枢与大脑集成 (3-4周) 

部署 Chatwoot 与 Dify，打通自研网关 ↔ Chatwoot ↔ Dify 之间的数据流 。

导入产品知识库，配置系统 Prompt，进行意图识别测试与人工转接演练 。


阶段 4：全量接入与 AI 调优 (2-3周) 

完成小红书、淘宝等剩余渠道的 API 对接与联调 。

通过沉淀的真实聊天日志，持续调优大模型回复置信度与话术库 。


阶段 5：灰度上线与压测预演 (1-2周) 

执行全链路压力测试，验证系统承载能力 。

在部分渠道/产品线灰度上线，建立日常监控与接口异常告警机制 。

九、 技术决策记录

| 决策项 | 选择 | 理由 |
|--------|------|------|
| 网关开发语言 | Go | 开发效率高，并发模型成熟，生态丰富，适合网关场景 |
| 客服工作台 | Chatwoot (开源) | 成熟的多渠道客服平台，减少前端开发量，通过 API 集成 |
| AI 编排平台 | Dify (开源) | 多 Agent 编排 + RAG 能力，支持按产品线隔离知识库 |
| 数据库 | PostgreSQL + pgvector | 同时满足关系型数据和向量检索需求，减少组件复杂度 |
| 部署方案 | K3s 容器化 | 轻量级 K8s，适合多云节点私有化部署 |
