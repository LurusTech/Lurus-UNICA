# Active Task: 存量产线补建知识库（配置面重构 阶段 3 · D8）

## Context
`doc/plan-config-surface.md` 第六节「阶段 3」。三条零售线（FreshMart / MegaStore / TechZone）
**有 Dify 应用但根本没有数据集**，实机确认：十条产线里只有这三条的 `config_json` 缺 `dify_dataset_id`。
它们的本体都已发布（各有 1 版活跃），提示词都对齐平台模板，唯独知识检索这一环是空的——
而且**没有任何入口能补上**：`CreateDataset` 全仓只在开户流程里被调用一次，
门户诊断卡检测得出"没有数据集"却故意不给按钮，代码注释自陈 "no endpoint does yet"。

根因在 `provisionDifyLine` 的幂等早退：它**只看 `dify_agent_id`**，
有 app 就直接返回"已配置"，从不检查数据集。于是"有 app 无 dataset"是一个
重跑开户也走不出去的死状态。

## 阶段 3 的真实范围比计划原文小得多

计划原文写的是"检索方式/top_k/rerank、分段规则收进门户"。逐项核对之后，
其中大部分已被后续设计**明确否决或已经做掉**，不应再算作未完成项：

- `top_k` —— S11 已做成 admin 可写（1–10，拒 0）。
- `rerank` / `score_threshold` / `indexing_technique` —— 计划 A 第 5 节逐条否决，
  理由分别是"失败即静默空召回""无法预先校验""改错即全租户上传失败"。
- **分段规则租户覆盖** —— 同节否决：没有重建索引的链路，做出来只对新文档生效，
  检索质量会变成"取决于文档哪天传的"随机变量。
- `search_method` —— 只需要"修复到与索引技术自洽"（`repairRetrieval` 已有），
  不需要自由选择；自由选择正是上面那条"改错即恒空"。

**所以本增量只做 D8 这一件事**：让"补齐一条线"成为可重入的操作，并给它一个入口。

## 为什么是这个顺序

**一、必须先修 D7 定的那条判据，否则这个增量在跟已有定案相反。**
D7（两套并行 provisioning）在 2026-08-13 定案："`admin/internal/bridge/dify.go` 是唯一实现，
**『已配置』判据只认 `dify_agent_id`**"。那条定案解决的是"两套实现互相打架"，
可它顺手把判据钉在了单一字段上——**而这正是 D8 的根因**。
本增量要显式修订它：唯一实现这一半继续有效，判据那一半改为**逐项自查**。
不写清楚这件事，下一个读 D7 的人会以为我们违规。

**二、光把早退条件改成"app 和 dataset 都在才早退"是错的，而且更危险。**
那样一条有 app 缺 dataset 的线会重新走完整个流程，**再建一个 app**。
正确的形状不是换一个早退条件，而是**取消整体早退，让每一步自查自己的前提**：
有 app 就不建 app，有 dataset 就不建 dataset，没挂载就挂载，检索不自洽就修。
开户从"全建或全不建"变成"把这条线补齐到规范"。补建入口和开户因此是同一段代码——
**再开一条建库路径就是 D7 的复发**，那正是 D7 花了一次定案才收敛掉的东西。

**三、"静默无效"的那几步必须先升级为会被报告的失败，再谈入口。**
当前 `AttachDataset` 失败只记 warning，`CreateDataset` 内部的检索设置失败也只记 warning。
但**漏了挂载，上传照常成功、索引照常完成，没有一条回答会用到它，且无任何报错**；
检索方式没设对则是"能查但查不到"。这两个正是 D8 最初形态的病根。
在给出"补建"按钮之前先把它们变成可见的失败，否则新按钮会造出一批
"点了成功、体检全绿、知识库照样不生效"的线——比没有按钮更糟。

**四、验收标准是"答得出来"，不是"库建出来了"。**
S11 已经把测试消息做成了能回显召回条数、来源文档与相似度的仪器。
本增量因此第一次有条件把验收下沉到真实效果：传一篇文档、问一个只有它答得出的问题、
**在页面上看见那几段被召回**。只验"数据集存在"会正好漏掉第三条里说的两种静默失效。

## Step-by-Step Plan

### 接线（先让"补齐"这件事存在且可重入，再谈按钮）

- [x] 1. **抽出"把一条线补齐到规范"的单一实现**（`ensureDifyLine` 或同义），
      `provisionDifyLine` 改为调用它。取消整体早退，改为逐步自查：
      app 在就跳过建 app、dataset 在就跳过建 dataset、未挂载就挂载、
      检索与索引不自洽就修、`config_json` 缺 id 就写回。
      每一步返回"做了 / 已经就位 / 失败"三态，而不是布尔。
      **不新增第二条建库路径**——这是 D7 定案要防的东西。
      *完成标志*：对一条完好的线跑两次，第二次全部报"已经就位"且不产生任何 Dify 写入；
      对一条有 app 无 dataset 的线跑一次，**只建数据集，不再建第二个 app**。

- [x] 2. **把三处静默失效升级为会被报告的失败**：挂载失败、`CreateDataset` 内部
      设检索方式失败、`config_json` 写回失败。三者各自都能造出"体检全绿、
      答案完全不用知识库"或"能查但查不到"。
      开户流程仍不因它们中断（新租户不该因为一次挂载失败开不了户），
      但结果里必须逐项列出**这条线现在缺什么**，而不是塞进一句 warning。
      *完成标志*：构造挂载失败，开户仍返回成功但结果里明说"数据集已建、未挂载，
      知识库不会被使用"；诊断卡据此判为断开。

- [x] 3. **空数据集的索引技术为空，不能被 S2 的拒写守卫挡住。**
      实机观测到：Dify 是在**首次上传文档时**才确定 `indexing_technique`，
      新建的空数据集报的是空值。而 S2 给 `SetDatasetRetrieval` 加的守卫是
      "索引技术不匹配就拒写"——照直觉实现，**新建库的第一次检索设置会被自己的守卫拒掉**，
      正好卡死这个增量要建的东西。
      空值视为"尚未定型"，按平台默认设置并放行；**只有读到一个明确且不匹配的值时才拒写**。
      *完成标志*：新建空数据集后能设上检索方式；把一个 economy 库谎报成语义检索仍被拒。

- [x] 4. **新端点：补建知识库。** `POST .../ai-settings/knowledge/provision`，**仅 admin**，
      落在 `bindDataset` / `repairRetrieval` 旁边——那两个知识库修复已经在这里，
      第三个放到别处只会让人多找一个地方。内部调步骤 1 的实现。
      幂等：已经就位的线返回"无需补建"而不是报错。
      **同改三处**：`aiSettingsPaths`、模块内 switch、门户调用——少一处就是 404。
      *完成标志*：对三条零售线之一调用一次，数据集建出、挂上、检索设对、
      `config_json.dify_dataset_id` 写回；再调一次返回"无需补建"。

### 实机又揪出三处，都已修并补测

**一、这个增量自己造出来的缺陷：新建数据集的 top_k 落在 2 而不是平台默认 6。**
新库带着 Dify 自己的 `top_k=2` 出生，而 `GetDatasetConfig` 会把当前 top_k 读进 `Overrides`
（S11 为了不让「修复检索」冲掉管理员设的值），于是那个 2 被当成"管理员的选择"永久保护住
——写 2、回读 2、校验通过、报"已按本部署的索引方式设好检索"。
**建库与修复不是一回事**：一个刚出生一毫秒的数据集没有任何选择需要保护。
建库路径现在显式写 `difyapp.DefaultTopK()`。既有测试没抓到它，是因为假件的初始检索模型是空的，
而真实的新建库带着 Dify 的默认值——测试已按真实情况重写。

**二、开户路径把"停下来之前建出来的东西"整个丢掉**（评审发现）。
`CreateChatApp` 成功而 `CreateAppAPIKey` 失败时，那个 app 只存在于 Dify，
响应里 `dify_agent_id` 为空，再 POST 一次就会**建第二个 app**——硬约束二的事故形态
从错误路径绕了回来。现在失败也返回已发生的步骤，并点名被孤儿化的资源。

**三、"挂载状态读不到"被说成了"未挂载"。**
服务端在 `reason` 里分得清，但 `Attached` 两种情况都是 `false`，门户标题一律打成
"数据集未挂到 AI 应用"。方向虽然安全，但仍是把猜测报成事实，而且会派人去修一个可能好好的挂载。
改成三态（`*bool`，nil = 没读到），门户单列一行"挂载状态读不到"，
仍提供修复按钮（它是幂等的，只补真正缺的东西）。
