# Active Task: 提示词权威源回收（配置面重构 阶段 2）

## Context
`doc/plan-config-surface.md` 第六节「阶段 2」。提示词目前**只存在 Dify 里**，UNICA 没有本地副本：
改不可审计、错不可回滚、漂了不可发现、回推只能靠一次性脚本。上一轮（S8/S9）做完了**检测**
那一半——控制台每次写入记下指纹与"当时是否等于平台模板"，据此把"和模板不一样"拆成
"自己写的"与"被模板更新落下的"（后者就是 D16）。于是 D16 现在**看得见，但解不掉**：
每个租户只能自己登录、自己发现自己落后、自己点一次按钮，平台侧没有清单也没有入口。

本增量把权威源搬回 UNICA：库里存正文与版本，Dify 降为**投影**，
并给平台侧一张"谁落后了"的清单和一个显式的回推入口。
*验收（计划原文）*：改平台模板后能列出哪些租户落后，能一键回推。**直接解掉 D16。**

## 为什么是这个顺序

**一、把 seed 和 push 拆开，风险就不存在了。**
计划第七节点名的最大风险是"阶段 2 的第一次推送会覆盖手改"——某租户在 Dify 控制台手工改过
提示词，搬权威源时被冲掉。这个风险来自一个隐含假设：搬迁 = 把模板推上去。
本计划不这么做。**首次搬迁只读不写**：把每条线 Dify 里**现行的那份**读进版本表当 v1，
本地权威承认现状。手改过的租户，搬完之后本地权威就是他手改的那份，状态是"已自定义"，
回推清单默认不选他。真正的推送是后面独立的、逐条显式勾选的一步。

**二、dry-run 报告必须先于 seed，而不是先于 push。**
风险节要求"先做全量备份 + 差异报告"。报告要在**写库之前**出——一旦 v1 落库，
"Dify 里原本是什么"这件事就只剩备份文件能作证了。这与 S9 立过的判据同形：
`prompt_origin` 的首批打标之所以有价值，是因为它记下了一个**当时知道、事后不可恢复**的事实。

**三、版本表先于回推。**
回推是"把 A 推成 B"，没有版本表就没有 A——推完之后租户的旧自定义版本无处可寻。
计划 A 的风险节写着"提示词覆盖目前没有版本历史，一次误保存无法恢复到租户的旧自定义版本
（只能回到平台模板）"，并建议拿审计当廉价快照。审计里存的是 `promptDigest`（sha256 + 字数），
**指纹不能还原正文**。版本表是这条不可逆性唯一真正的解法，所以它排第一。

**四、跨租户清单与批量回推放 admin，不放租户页。**
落后是**平台模板动了**造成的，后果是平台级的；租户页只该回答"我这条线怎么样"。
把批量入口放进 `ai-settings`，租户会以为自己在操作一批东西——计划 A 已经立过这条判据
（「在 ai-settings 内做 admin 可写的平台分区」列在明确不做里，理由是**范围错觉比没有入口更糟**）。
单租户的回滚是自治范围，留在租户页。

**五、回推必须过 S8 的契约校验。**
契约校验现在只在租户页写入时挡。批量推不过校验的话，平台模板哪天缺了 `{{facts_context}}`，
一键回推会把全平台一起打瘸——这正是计划 A 风险节"S8 若把契约清单定错，会挡住所有租户"
那一条的对偶面：挡住所有人是麻烦，推瘸所有人是事故。

## Step-by-Step Plan

### 接线（先证明权威源真的存在、真的能比、真的能推）

- [x] 1. **迁移 019：`prompt_versions`**。比照 `ontology_versions`：`UNIQUE(product_line_id, version)`，
      活跃版本用**部分唯一索引**强制每条线只有一行 `active`。
      字段与 ontology 的差异要落在表结构上，不是注释上：
      - 没有 `compiled`——提示词没有编译步骤，正文即权威（`body TEXT`）。
      - 多 `template_sha256`——S9 已经在 `prompt_origin` 里存的那个事实，搬进版本表。
      - 多 `pushed_at`——**ontology 发布即生效（router 直接读库），提示词发布必须推才生效**。
        publish 因此是两段的：本地定版 + 投影推送，两段之间存在一个真实状态
        「已定版未生效」。`pushed_at IS NULL` 就是它。界面必须能说出这个状态。
      - `source`（console / provision / seed / template）——回推与手改在清单里要分得开。
      *完成标志*：迁移可重复执行；插两行 active 被数据库拒绝（不是被代码拒绝）。

- [x] 2. **版本表访问层**，放 `admin/internal/repository`，**不放 `pkg/`**。
      ontology 的 store 在 `pkg/domain` 是因为 router 也读它；提示词 router 从不读，
      只有 admin 读写。为对称而把不共享的东西放进共享包，是给下一个人一个错误的暗示。
      三个操作，都在事务里：`Publish`（`MAX(version)+1`，旧 active 置 false，新行 active）、
      `Rollback(version)`（同 ontology）、`List(productLineID)`。
      *完成标志*：单测覆盖"并发两次 Publish 不会产生两行 active"。

- [x] 3. **`promptaudit`：备份 + dry-run 差异报告**（Go cmd，不再写一次性脚本）。
      比照 `cmd/configparity` 的结构化对拍形态，而不是 `tmp/rollout_prompts.py` 的一次性形态——
      **模板每动一次这个报告就要能重跑**，一次性脚本第二次跑就没人信了。
      逐条产线输出：Dify 现行正文 sha256、平台模板 sha256、`prompt_origin` 现状、
      契约缺项、以及判定（一致 / 被模板落下 / 已自定义 / 控制台外被改 / 无记录）。
      同时把全部现行正文原样写进备份 JSON（形态比照 `tmp/prompt-backup-20260814.json`）。
      默认只读；`--seed` 才写库。
      *完成标志*：不带 `--seed` 跑完之后 `prompt_versions` 仍是空表；报告里每条线都有判定，没有"未知"兜底项。

- [x] 4. **首次搬迁（`--seed`）：把现行正文读进版本表当 v1，一个字都不写回 Dify。**
      幂等：已有版本的线跳过。`source='seed'`，`pushed_at` 置为当前时刻
      （投影此刻确实等于本地权威——这是搬迁那一刻唯一为真的事）。
      `template_sha256` 取自 `prompt_origin`（有记录的）或当场比对（无记录的）。
      *完成标志*：全部产线各有一行 v1；对每条线做一次读回，正文与备份 JSON 逐字节相同；
      **Dify 侧未发生任何写入**（比对搬迁前后的 Dify 更新时间）。

- [x] 5. **`updatePrompt` 改为「先定版、后投影」**，并如实回报投影结果。
      顺序不能反：先写 Dify 再写库，中间失败就出现"生效了但库里没有"——那正是要消灭的状态。
      推失败时版本保留、`pushed_at` 为空，响应里带 `pushed` 布尔与失败原因，
      比照 S3 的 `cache_invalidated`——**接口说实话，界面才有得可说**。
      契约校验（`difyapp.MissingPromptRequirements`）仍在最前，位置不变。
      同一步把开户流程（`tenants_provision.go`）也接上：新线创建应用后落 v1，
      否则新租户从出生起就是"无记录"，S9 刚修好的自称问题会以另一种形式回来。
      *完成标志*：断开 Dify 后保存一次，返回 200 且 `pushed:false`，库里有新版本；
      恢复后重推成功，`pushed_at` 补上。

- [x] 6. **单租户回滚**：`POST .../ai-settings/prompt/rollback`（body 带 `version`），租户自治。
      这一步解掉计划 A 风险节点名的那条不可逆性。回滚同样是"定版 + 投影"两段。
      **同改三处**：`aiSettingsPaths`（`main.go` ~452）、模块内 switch（`aisettings.go` ~333）、
      门户调用——少一处就是 404。
      *完成标志*：保存一版新的，再回滚到上一版，Dify 里的正文逐字节回到旧值。

### 实机又揪出两处，都已修并补测

**一、平台回推不写 `prompt_origin`，把自己报成"控制台之外被改过"。**
回推写了版本表和 Dify，却把兜底记录留在旧文本上，于是被平台正当推过的线，
在以 origin 为准的那个视图里变成"有人直接在 Dify 改过"——**假警报正好出在
运维会去看的地方，而且是本增量旗舰操作触发的**。改为投影成功后同写 origin，已补回归测试。

**二、回推的审计行没有 `before`。**
原实现留了理由："替换掉的那一版在版本表里有行"。但版本表**不记录某一版何时停止活跃**，
而回滚会让旧行重新变 active 且不新建行——一旦发生过回滚，`created_at` 的顺序就不能
还原"某时刻在效的是哪一版"。现在记前一版的**版本号**（不是正文，审计表不做第二个提示词存储）。

### 一个运维陷阱（不是缺陷，登记备查）

平台模板是**编译期常量**，所以两个不同时间编译的二进制会对"平台模板是什么"给出
**自信而相反**的判定：演练中用改模板前编译的 `promptaudit` 去读改模板后的部署，
10 条线的判定整个倒挂，且两边都不报警。缓解已经在位——清单与报告都吐 template 哈希，
比一下即可发现。换模板时 `admin` 与 `promptaudit` 必须一起发。

### 代码之外，本轮多做的三件事

**一、`UpdateSystemPrompt` 补上回读校验。** 桥在同一个文件、同一个端点上已经写明了判据：
附加数据集的写入「is verified rather than trusted —— Dify 对一个什么都没改的 model-config 写入，
回的是和真生效一样的 200」。而提示词走同一个端点却不校验。这正是本增量要消灭的"200 但没生效"：
`pushed:true` 此前只代表"Dify 收下了"。逐字节比对是安全的，因为**这个前提 S9 已经实测过**
（行尾空格、制表符、零宽字符、ZWJ emoji、400 字长行，读-改-写 sha256 相同）。
两条测试钉住它：桥层一条（静默吞掉的写入必须报错），端到端一条（整条链路必须说"已保存、未生效"）。
连带把两处假 Dify 从静态桩改成会记住写入的——它们此前答得起"old"，是因为没人回读。

**二、评审抓到一个会把 D16 造回来的真缺陷。** `storeRevision` 原本要求
`TemplateSHA256` 也相同才复用活跃版本，而这个值是拿**今天**的模板算的，
对"当年就是模板、模板后来变了"的正文恒为空。于是平台模板一改，租户点一次"重新推送"
就会新开一版 `template_sha256=''`，被判成"已自定义"，**从回推清单上消失**——
正是本增量要解的那件事又被造出来一条。改为复用只看正文，已补回归测试。

**三、审计动词补 `push`（迁移 020）。** 014 把 `audit_logs.action` 钉成封闭 CHECK，
平台回推写的 `push` 不在其中，会被数据库整行拒收——正好丢在"审计逐条记"那个地方。
没有复用 `publish`：本增量刚把"定版"与"投影"拆成两个真实半段，
用一个词记两件事，事后没法回答纠纷问的是哪一半。另有一条测试从迁移里读回词表反查 Go 里的字面量。
