# AI 设置页收拢方案

> 目标（用户原话）：**"在工作台的 AI 设置卡片，把能用的设置都集中在这里，其他先等等。没有的现在做。"**
> 本文只是方案，不含实现。产出自一次 8 agent 的调研编排（枚举 → 真伪校验 → 可行性 → 对抗审查 → 综合）。
> 规划层模型额度不可用，综合环节回落到实现层模型产出。
> 最后更新：2026-08-24

## 零、主会话复核：两条最响的结论被我核减了

调研报告不能直接采信。下面两条是它篇幅最重、措辞最强的发现，我逐条到代码与实机里验了，
结论**与报告不一致**，方案里相关步骤的优先级和验收标准需要按这里的事实改写。

### 0.1 「应用未声明变量导致 inject_facts / SCENE_MODE 空转」——机制为真，**当前没有发生**

机制确实存在，而且代码注释里早就写明了（`pkg/difyapp/prompt.go:23`）：
"Dify silently drops an input that the app has not declared"。

但实机探针查了五条产线的 `user_input_form`：

```
XDYX       声明=facts_context,scene_context,experience_context,knowledge_context,customer_name,channel,product_line
AJYJ       同上
MegaStore  同上（顺序不同）
TechZone   同上
FreshMart  同上
提示词里实际用到：facts_context, scene_context, experience_context, knowledge_context
```

**七个变量全部声明齐全，提示词用到的四个一个不缺。** 所以：

- 报告称这是"本次最大漏项"——**过了**。它是一道**预防性**体检，防的是手工改过的应用与未来开户漏配，不是在修一个正在发生的故障。
- S4 的验收写的是"拿一个缺 `scene_context` 的老应用"——**当前五条线里没有这样的应用**，这条验收跑不起来，得改成构造性验证。
- 风险一节称 S4 会让"一批租户第一次真的开始收到 facts_context / scene_context"从而金标必然漂移——**对这五条线不成立**，它们一直在收。S4 对现有金标应当是零影响。

### 0.2 「handoff_keywords 一条都不生效」——条件为真，**当前不成立**

`evaluator.go:190` 确有此事："Under TriageOn the keyword rules are retired"。
但当前部署的 `router.env` 没有设 `INTENT_TRIAGE`，落到默认值 **shadow**
（`triage.go:36` `DefaultTriageMode = TriageShadow`，不是 off——实机 `/configz` 已确认）。
`EvaluateWithMode` 的注释写明**只有 `TriageOn` 才弃用关键词表**，shadow 下"keyword list still applies"，
所以关键词表现在是**正常生效**的。

这是一条**潜在**缺陷：等哪天把 triage 打开，整份关键词表会静默失效，而门户仍写着"立即生效"。
界面上要认账没错，但它不是当下的故障，不该排在止血序列的前面。

### 0.3 这两条核减不影响方案主干

页面结构、取舍原则、以及"接线与暴露必须分开"这条纪律都成立。
受影响的只是 S4 的优先级（从"最大漏项"降为预防项）与 S6 的紧迫性（从现存故障降为潜在故障）。

# AI 设置页收拢计划

## 1. 取舍原则（一句话）

**只有"这个租户改了它、这个租户的下一条回答会不同、且我们能在写入时校验它真的落到了生效点"的项，才进这一页的可写区；改不了但能解释租户看到的行为的，进只读区并且必须显示"实际生效状态"而不是配置里的裸值；其余一律不进。**

这条原则里最硬的是后半句。对抗审查找出的问题有一半不是"没开关"，而是**有开关、值也真、但被上游一个租户看不见的条件整体作废**（handoff_keywords 被 `INTENT_TRIAGE=on` 跳过；inject_facts 被 `ONTOLOGY_ENABLED` 或未声明的 `facts_context` 作废）。所以在这一页上把裸布尔值搬过来展示，是在制造新的假开关。**只读区展示的单位是"生效/未生效 + 卡在哪一环"，不是配置值。**

## 2. 最终页面结构

**排序按"影响回答的先后"（流水线顺序），不按修改频率。** 理由：这一页真正的失败模式不是"找不到常用项"，而是"改了一个开关被上游作废却毫无提示"。按流水线排，上面的卡片天然是下面卡片的前置条件，依赖关系靠位置就说清楚了；按频率排会把体检信息埋到中间。

| # | 卡片 | 权限 | 内容 |
|---|---|---|---|
| 0 | **接通体检**（新增，置顶） | 只读 + admin 可点修复 | 逐行诊断：Dify 应用声明了哪些上下文变量（facts/scene/experience/knowledge_context，缺哪个红标）· 是否绑定数据集 · 数据集检索方式是否与其索引技术匹配 · 平台总闸 `ONTOLOGY_ENABLED`/`INTENT_TRIAGE`/`SCENE_MODE` 当前档位 · 本体是否有已发布版本。每行 ok/warn pill，warn 行写明卡点。修复按钮：补齐变量声明、绑定数据集、修复检索设置。 |
| 1 | 系统提示词 | 租户可写（加契约校验） | 现有编辑框 + 必需占位符与标签协议硬校验 + 与平台模板的漂移 pill + 「恢复平台模板」 |
| 2 | 知识与检索 | admin 可写 / 租户只读 | 数据集绑定修复、检索设置修复（含 indexing_technique 匹配前置校验）；只读展示：索引技术、分段规则、当前 top_k |
| 3 | 事实与校验 | **只在体检卡里出现诊断行，表单不搬** | 见下 |
| 4 | 转人工与阈值 | 租户可写 | 现有四项 + 阈值旁显示"本租户当前可达的最高置信度"及其依赖链 + triage=on 时关键词区置灰并注明"已由意图分诊接管" |
| 5 | 满意度调研 | 租户可写 | 现有三项 + 新增提问语/感谢语 + 标注 timeout 仅对此后新发出的调研生效 + 只读显示平台 `IDLE_TIMEOUT`（决定何时发起） |
| 6 | 生效模型 | 纯只读 | 维持现状 |
| 7 | 测试消息 | 诊断 | 扩展为回显召回条数/来源数据集/本次实际注入了哪些变量——这是全页唯一的反馈回路 |

**关于本体三块（inject_facts / validation / breaker）的硬结论：表单留在 ontology.html，不搬。** 边界判据是**配置 vs 内容**：ai-settings 收的是"AI 怎么答"的配置，ontology.html 管的是"事实条目"这份内容及其发布，而这三个开关是那份内容的使用方式，跟内容放在一起是对的。ai-settings 这一页只在体检卡里给一行「事实注入：实际未生效 —— 平台总闸已关闭 / 应用未声明 facts_context / 本产线无已发布版本」。**绝不放一行 `inject_facts: on` 的只读摘要**——那正是新假开关。

**平台级配置不进这一页的写入区，也基本不进它的只读区**，去 admin.html 的 panel-ops 加一张只读卡；进这一页只读区的门槛是"租户能用这条信息解释自己看到的行为"（总闸档位、索引技术、IDLE_TIMEOUT 属于此列，ACEST 队列长度、缓存 TTL 不属于）。明确否决"在 ai-settings 内做平台设定分区且 admin 可写"：这一页从 URL 到渲染全按租户参数走，在租户上下文里放全局写入口是把跨租户事故伪装成单租户操作。

## 3. 逐项决策表

| 候选项 | 决策 | 理由（一句话） |
|---|---|---|
| Dify 应用变量声明对拍（facts/scene/experience/knowledge_context） | **放（体检卡第一行）** | 未声明的 input 被 Dify 静默丢弃，这是 inject_facts/SCENE_MODE 变成假开关的真正机制，也是本次最大漏项 |
| 数据集检索设置一键修复 | **放，但先补前置校验** | 生效路径已存在且幂等；但必须先 GET 数据集读回 indexing_technique 比对，否则会把 economy 库改成语义检索、检索恒空且回读校验发现不了 |
| 数据集绑定修复 | 维持（已在） | 不接参数、幂等、写后回读，是唯一正确形态 |
| 数据集 top_k | **先接线再放，排最后，限 admin** | 「single/router 模式下取数据集 top_k」目前只是假设，仓库两次栽在同类假设上；必须先让测试消息回显召回来源自证，且回读校验扩到 top_k |
| score_threshold / reranking_enable | **不放** | 前者失败模式是静默召回为空且门户看不到召回；后者我们无法查询 workspace 有无 rerank 模型，打开可能整库报错 |
| 「修复检索」与「租户 top_k」并存冲突 | **结构上一次做对** | `SetDatasetRetrieval` PATCH 的是完整对象，从 S2 起 want 就构造成「平台默认 + 租户覆盖合并」，否则两个按钮会在同一张卡上互相静默回滚 |
| 系统提示词 | 维持可写 + 加契约校验 | 目前除非空外零校验，租户删掉 `{{facts_context}}` 后指标照常自增而模型什么都收不到 |
| 提示词权限方向 | **反过来** | 现在"覆盖不需要 admin、恢复需要 admin"；改成覆盖要二次确认+契约校验、恢复平台模板对租户开放 |
| 提示词写入审计 | **必须补** | AuditState 只快照 config_json，提示词权威源在 Dify，改动最大的两个操作留下 before/after 完全相同的审计行 |
| 平台模板漂移 pill（D16） | **先验证再放** | 对拍靠字节 hash，而 pre_prompt 经历过 Dify 的读-改-写，任何规范化都会让租户永久显示"已自定义"、永不提示同步，比没有提示更糟 |
| guardrail 四项（阈值/关键词/屏蔽话题/等待语） | 维持可写 | 真实生效，证据充分 |
| handoff_keywords 的条件性失效 | **必须在界面上认账** | `INTENT_TRIAGE=on` 时整份关键词表被跳过一条不生效，而卡片文案写着"立即生效"；README 已表明平台方向就是开到 on |
| confidence_threshold 的离散语义 | **显示可达上限** | 置信度只有 0.3/0.72/0.75/0.90 等离散档，填 >0.90 即 100% 转人工，而提示写得像连续可调 |
| `ConfidenceThreshold == 0` 回填 | **代码里写死约束** | 零不可表达，今天靠三层校验碰巧一致，哪天加个"停用"选项就引爆 |
| ontology 写入不失效 route cache | **必须修（且抽共享实现）** | 关 enforce 止血最长 5 分钟不生效；更糟的是顺手保存一次 guardrail 就会冲掉缓存，导致该缺陷间歇性消失、无法复现 |
| `invalidateRouteCache` 静默 return | **一并修** | admin 未连 Redis 时同样退化，门户却无条件承诺"立即生效" |
| 调研提问语 / 感谢语 | **先接线再放** | 客户直接看到的文案却是 Go 常量，与已开放的 holding_message 没有区别对待的理由 |
| survey timeout_hours 语义 | **加一行说明** | TTL 在发送那刻一次性写进 Redis，改配置对在途调研无效 |
| IDLE_TIMEOUT | **只读展示在调研卡** | 租户能配开关/门槛/超时，唯独"什么时候发"由平台 env 决定，这是层级错配，至少要可见 |
| difyConvTTL（多轮上下文 24h） | 平台页只读 | 改变 AI"记得多久"，但包级常量、全平台一份 |
| 分段规则 process_rule 租户覆盖 | **不做** | 存量文档不会重切，且仓库里根本没有 update 端点、也不保存源文件，无法重建；做出来就是"库内检索质量取决于文档哪天传的" |
| indexing_technique | 只读展示 | 部署期约束，改错表现为全租户上传失败 |
| INTENT_TRIAGE / SCENE_MODE 租户化 | **不做** | 现状进程级一份值管所有租户，租户化要改判定热路径，且会毁掉 shadow 观测的可比性 |
| intent 六张词表 / 三段 scene 策略正文 | 平台页只读展示 | 它们才是 triage=on 后真正决定转人工的东西，且策略词表是按零售调的，非零售租户开 SCENE_MODE 近乎无效 |
| 转人工摘要提示词 summaryPrompt | 登记，本轮不做 | 又一处 Go 常量 LLM 调用，且不剥离 `[FACT:]/[HANDOFF:]` 标签，坐席可能看到协议标签——是独立缺陷，不是配置项 |
| `[INTENT:]` 词表与模板脱钩 | 登记 | 模板已无该规则，链路恒为空；提醒本次要为提示词列出"契约清单" |
| 模型 / 供应商 API key / Dify 凭据 / Chatwoot 块 / dify_dataset_id 直编 / harmTopics / ACEST 全套 / ONTOLOGY_CACHE_TTL | **不放** | 分别是平台决策、凭据、假开关、安全底线、运维参数 |

## 4. 分步实施计划（接线与暴露严格分离）

**S1 · 接线：router 暴露只读配置端点。** router 加 `/configz`（内网、admin 服务侧拉取并短缓存），返回 `INTENT_TRIAGE`/`SCENE_MODE`/`ONTOLOGY_ENABLED`/`ONTOLOGY_CACHE_TTL`/`ROUTE_CACHE_TTL`/`IDLE_TIMEOUT`/ACEST 是否启用。
*验收*：admin 侧打印出的值与 router 容器实际 env 一致；改 env 重启 router 后 admin 读到新值。**这是 S5/S6/S10 的唯一正解**——admin 的 Config 里一个都没有，照原方案直接读自己的 env 会自信地显示相反的值。

**S2 · 接线：Dify 数据集读写能力补全。** 抽出可复用的"读数据集当前 retrieval_model + indexing_technique"方法；`SetDatasetRetrieval` 写入前比对索引技术，不匹配则拒写并报"请先重建索引"；回读校验从只校 search_method 扩到 top_k / score_threshold_enabled / reranking_enable；want 改为「平台默认 + 租户覆盖合并」的构造形态（此时租户覆盖恒为空）。
*验收*：单测覆盖三种不一致；对一个真实数据集，故意让 env 与库的索引技术不一致，必须拒绝而非打印成功。

**S3 · 接线：缓存失效统一。** 把失效逻辑抽到共享位置，facts 的 putConfig 接上（需改构造函数与 main 接线），aisettings 的静默 return 改为 WARN 并在响应里返回 `cache_invalidated`；门户"立即生效"文案改为按该字段渲染。
*验收*：改 validation 后秒级观测到 router 行为变化；断开 admin 的 Redis，门户不再声称立即生效。

**S4 · 接线：应用变量声明对拍与补齐。** 读回 user_input_form 与期望变量集合比对，复用现有的幂等补齐能力。
*验收*：拿一个缺 `scene_context` 的老应用，检测报缺失 → 补齐 → 复检通过 → `SCENE_MODE=on` 下回答确实产生变化（这一步同时证明了 scene 注入此前是空转）。

**S5 · 暴露：体检卡上线。** 数据全部来自 S1/S2/S4，不新增数据源。
*验收*：三条无数据集的零售线与 ajyj/xdyx 分别打开，一眼看出各自卡在哪一环；页面上不出现任何裸布尔值。

**S6 · 暴露：转人工卡片认账。** triage=on 时关键词区置灰 + "已由意图分诊接管"；阈值旁显示本租户可达的最高置信度与依赖链。
*验收*：把 `INTENT_TRIAGE` 从 off 改到 on 重启 router，门户关键词区自动置灰，无需改前端。

**S7 · 接线→暴露：调研文案。** 先扩 pkg/survey 字段并让两条链路真的读它；感谢语路径**用回查产品线后加载配置**的方式拿到 cfg，**不扩 pendingSurveyData**（扩了会让改动上线那刻所有在途 pending 反序列化出空串，正撞上刚修过的"空答复不得投递"）；两条文案一律走 IsBlankAnswer 回落、限长 500。接线验收通过后再上表单。
*验收*：先直接改库里的字段（不经门户）确认客户收到的两句话变了；再上表单。

**S8 · 暴露：提示词契约校验 + 权限对齐 + 审计补全。** 必需占位符与 `[FACT:]/[HANDOFF:]` 标签协议列成显式清单并在保存时硬校验；覆盖操作加 diff 二次确认；"重置"改名"恢复平台模板"并对租户开放；AuditState 纳入 pre_prompt 的 hash 与长度。
*验收*：删掉 `{{facts_context}}` 保存被拒；审计表能看出前后 hash 不同。

**S9 · 暴露（前置验证后）：平台模板漂移 pill。** 先在真实 Dify 上验证"写进去再读回来字节完全相同"；不成立则改用对规范化不敏感的比较，再上 pill。
*验收*：改平台模板一个字，存量租户显示"平台模板已更新，本租户仍在旧版"，自定义过的租户不误报。

**S10 · 暴露：admin.html 平台设定只读卡。** 数据来自 S1 + 编译期常量（默认模板全文、默认 guardrail、分段规则、intent 词表、三段 scene 策略正文），每项标注来源与生效方式（"env · 需重启 router" / "编译期常量 · 需发版"）。凭据类只显示"在 Dify 控制台管理"+ 连通性状态，不显示值也不显示掩码。
*验收*：运维不再需要 ssh 就能回答"当前 INTENT_TRIAGE 是几档"。

**S11 · 接线→暴露：测试消息回显召回，然后才谈 top_k。** 先让测试消息显示召回条数/来源数据集；用它证明 top_k 确实改变召回之后，再把 top_k 做成 admin 可写（1–10，拒绝 0），写入走 S2 已经做对的合并构造。
*验收*：同一问题在 top_k=2 与 top_k=8 下召回条数不同且可见。

**跨步骤硬约束**：每个新端点必须同改三处（闭合路由表、模块内 switch、门户调用），少一处就是 404；任何新写入 config_json 的块必须同步进 AuditState，否则留下 before/after 相同的审计行。

## 5. 明确不做

- **分段规则租户覆盖**——没有重建索引的链路（无 update 端点、不保存源文件、无正文回取方法），做出来只对新文档生效，检索质量变成"取决于文档哪天传的"随机变量。
- **top_k 开给租户 user**——受影响的是仓库里的金标文件和 CLI 重跑入口，租户既够不着也收不到信号，回归测试会在某天开始飘而无人知道起因。
- **score_threshold / rerank / indexing_technique 可写**——分别是"失败即静默空召回""无法预先校验""改错即全租户上传失败"。
- **triage / scene 租户化**——热路径改造 + 毁掉 shadow 观测的可比性。
- **平台凭据进门户**——前置条件不成立（AES key 缺失目前只告警不致命），且爆炸半径是全平台而门户只有原生 confirm()。
- **在 ai-settings 内做 admin 可写的平台分区**——范围错觉比没有入口更糟。
- **"配置来源/已覆盖"标注与"恢复默认=删字段"**——**本轮不做**。写入路径是整块回写且字段无 omitempty，凡在门户保存过一次的租户，"显式覆盖 vs 吃默认"的区分在数据里已经不存在，现在做只会稳定输出错误信息；而且删字段这个操作在当前审计快照（回填后的值）下 before/after 完全相同。要做得先改写入语义，那会牵动共享结构体和 router 的读取语义，不属于本轮。

## 6. 风险

**会让存量金标漂移的**：S4 补齐变量声明——这是本计划最大的行为变更，一批租户会**第一次真的**开始收到 facts_context / scene_context，回答必然变化，`testdata/golden/*.yaml` 与 baseline 必须重跑；S2 的检索设置修复在索引技术不一致时会改变召回集（但那种不一致本身就是故障）；S11 的 top_k。

**影响所有租户的**：S1 暴露的 env（只读，不改值）；S10 展示的平台模板与词表——一旦有人据此去改常量，改的是全平台转人工率；S8 若把契约清单定错，会挡住所有租户的提示词保存。

**不可逆的**：提示词覆盖目前没有版本历史——S8 之前，一次误保存无法恢复到租户的旧自定义版本（只能回到平台模板）。建议 S8 把旧值写进审计当作事实上的快照，这是最低成本的可回滚手段。S4 的变量补齐本身幂等可逆，但**它引发的行为变化不可逆**——注入一旦接通，此前被掩盖的提示词缺陷、事实缺失、非零售租户 scene 策略不匹配都会同时暴露，建议按租户分批做，先在一条线上观察一轮再铺开。

**间歇性缺陷的特别提醒**：S3 修复前，ontology 缓存缺陷会因为"顺手保存过 guardrail"而随机消失，任何现场复现都不可信；不要在 S3 之前根据现场表现下结论。
