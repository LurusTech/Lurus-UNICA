# 工作台设置面收拢（配置面重构 阶段 4）

本文只做设计，不含实现。盘点依据为 2026-08-26 的代码核对与实机验证。

## 前提变更（2026-08-26）

用户明确本项目**为私用**。这条前提推翻了此前若干基于"多租户互不信任"的决策——
凡是理由为"防止租户 A 看到租户 B"或"防止租户改坏"的约束，一律重新评估。
技术性风险（改了会静默失效、会出空回复）不因私用而消失，那些约束保留，
但处理方式从"藏起按钮"改为"给出按钮并把风险摊开"。

**若将来本项目转为对外多租户，本文第一条与第四条必须回滚**，
第八条的模型可写也需重新评估——那时租户改模型会直接影响成本与彼此的服务质量。

## 出发点

用户原话（2026-08-26）：

> 尽量不要让用户经常去 dify 里面找设置，chatwoot 还好点，因为用户经常要在这里用。

以及：

> 配置 ai 模型的设置我看工作台是不能改的

这句话把目标往前推了一格。`plan-config-surface.md` 定的是**权威归属**——配置的真值存在 UNICA 库，
外部系统只是执行副本。本文要的是**日常动线**：租户在一个正常的工作日里，不应该有理由打开 Dify。

两者不是一回事。权威已经收回来了，但只要还剩一件事必须去 Dify 才能做，租户就还得记住那个地址、
那个账号，以及"哪些东西在哪边改"——而这正是 `plan-config-surface.md` 开篇要消灭的东西。

Chatwoot 不在此列。坐席本来就在 Chatwoot 里接待会话，那是它的主场，不是"被迫跑一趟"。

## 现状盘点

### 租户已经不需要 Dify 的部分

| 租户想做的事 | 现在在哪 |
|---|---|
| 传文档、删文档、看索引进度 | 门户「我的知识库」 |
| 改系统提示词 | 门户「AI 设置」，含版本历史与回滚 |
| 调召回条数 top_k | 门户「AI 设置」 |
| 试一句话看 AI 怎么答 | 门户「AI 设置」测试消息 |
| 看这句话召回了哪几段、来自哪篇文档、相似度多少 | 门户「AI 设置」测试消息 |

### 唯一还需要 Dify 的部分

**看某篇文档被切成了什么样的分段。** 文档传进去之后切得对不对、有没有把一句话拦腰截断、
某个关键条款有没有被拆到两段里去——这些只有 Dify 的文档详情页能看。门户里没有任何入口。

这是本轮要补的缺口，补上之后租户的动线就闭合了。

## 决策

### 一、Dify 入口：提供（2026-08-26 改判）

**原判：租户侧不做。现改为做。** 原否决理由是越权，而越权顾虑在私用前提下不成立。
下面保留原始分析，因为它记录的拓扑事实没有变，**转为对外多租户时这条必须回滚**。

免登录这一步的障碍与安全无关，是同源问题：门户在 3401，Dify 在另一个端口，
跨源无法把登录态写进 Dify 的 localStorage。两条路：

- **零开发**：直接给链接，靠浏览器记住 Dify 的登录态。体验是"第一次登一次，之后点开即进"。
- **推荐**：用 nginx 把 Dify 反代到门户同源路径下（如 `3401/dify/`）。同源之后后端可用
  已有的管理员凭据换 console token 直接种入，真正点开即进；顺带消掉"两个端口两个地址"的记忆负担。
  **前置验证**：Dify 前端能否在子路径下正常运行（部分应用硬编码根路径）。实机试通再写实现。

以下为原始分析，保留备查：

**（原判）租户侧不做，理由是拓扑硬约束。**

- UNICA 调 Dify 用的是**全平台一个管理员账号**：`DIFY_ADMIN_EMAIL` / `DIFY_ADMIN_PASSWORD` /
  `DIFY_ADMIN_TOKEN` 都是进程级环境变量（`admin/internal/config/config.go:19-23,68-72`），
  console token 缓存 30 分钟全租户共用（`bridge/dify.go:984-1010`）。
- 所有租户的 app 和 dataset 建在**同一个默认 workspace**里，靠 `UNICA-<产线名>` 命名前缀区分
  （`bridge/dify.go:267-360`）。租户之间的隔离依赖各自的 app-key 与 dataset-id，
  **不依赖 Dify 的账号或 workspace**。
- 「每产线一个 workspace」的旧方案已废弃，见 `router/cmd/setup_dify_workspaces/main.go:1-9`
  的包注释：当前唯一生效的拓扑是"一个 app + 一个 dataset，在默认 workspace 内，
  以 `dify_agent_id` 为 key"。这条路是走过又退回来的。

结论：让租户登进 Dify 控制台，他看到的就是全平台所有租户的应用、知识库和文档正文。
这不是权限配置能拧紧的，是拓扑决定的。

第二道坎：Chatwoot 的免密靠它特有的 Platform API（`GET /platform/api/v1/users/{id}/login`
换一次性登录链接，`bridge/chatwoot.go:255-272`），**Dify 社区版没有对等能力**——
没有"平台管理员代任意用户换登录链接"这个口子。即便隔离问题解决，免密这一步也没有现成的路。

**替代方案就是本文第二条**：把租户还需要 Dify 的那件事搬进门户，让"去得方便"变成"不用去"。

### 二、补齐文档分段明细

在「我的知识库」的文档条目上增加"查看分段"，读 Dify 的分段接口，在门户里展示：
分段序号、正文、字数、命中次数（若接口提供）。只读，不提供编辑——
分段是索引产物，改它等于重新索引，属于内容资产范畴，`plan-config-surface.md` 原则 2 划在 Dify 那侧。

补上之后，"租户不需要打开 Dify"这句话才成立。

### 三、Dify 入口的落点

平台管理页已有 Dify 控制台外链（`portal/admin.html:412`），工作台侧新增一个同样的入口。
免登录做法见第一条——同源反代是推荐路线，实机验证子路径可行性之后再写实现，
验证不通过就退回"直接给链接"，零开发。

### 四、运行开关分档

`plan-config-surface.md` 划分原则第 5 条："凡是有业务含义的开关，不许留在 env。"
但阶段 4 在计划里被标为"可不做"，于是下面这些至今仍锁在环境变量里、改一次重启一次。
这是方案自身的一处矛盾。逐个定档：

| 开关 | 现状 | 决策 |
|---|---|---|
| `INTENT_TRIAGE` | 三态 off/shadow/on，默认 shadow；全平台一份；重启 router 生效（`router/cmd/router/main.go:323`，`internal/guardrail/triage.go:38-56`） | **搬进数据库**，平台管理页可改、热生效；租户设置页只读可见 |
| `SCENE_MODE` | 同上三态，默认 shadow（`main.go:333`，`internal/routing/scene.go:8-51`） | 同上 |
| `ONTOLOGY_ENABLED` | env 总闸（默认 true）+ 已有的逐产线开关 `config_json.ontology`（`main.go:343`，`router.go:644-658`） | **总闸保持平台级**，但当前状态必须显示出来 |
| `DIFY_INDEXING_TECHNIQUE` | admin 级单值，默认 high_quality（`admin/internal/config/config.go:74`） | **可改（2026-08-26 改判）**，但必须同时显示每个知识库的实际索引方式，并在改动时明说存量不迁移 |

前两个之所以值得搬：它们是 shadow→on 的灰度开关，本来就要来回试，每试一次重启一次 router
代价太大。而且 `INTENT_TRIAGE` 一旦置 on，**租户的转人工关键词整个失效**——
租户现在只看到输入框灰掉和一句提示（`portal/ai-settings.html:2162-2181`），
看不到平台处在哪一态、什么时候会变。

`ONTOLOGY_ENABLED` 不需要"下放"：它已经是两层的，env 是事故总闸，逐产线开关本来就在数据库里、
租户在「确定性事实」页能自己开关。要补的是**显示**：现在如果平台把总闸关了，
租户该发布发布、该开开关，界面一切正常，但事实一条都不会注入——又一次静默失效。

`DIFY_INDEXING_TECHNIQUE`（**2026-08-26 改判为可改**）：它**只影响之后新建**的文档，
不动存量索引（`admin/internal/tenant/knowledge/knowledge.go:92-106`）。改一次，
库里就同时存在两种索引方式的文档，现象是"上传成功、索引成功、但一条也召不回，还不报错"——
正是上一轮在 DrillCo2/3/5 上抓到的病。

原判是"藏起按钮"，现改为"给出按钮并把风险摊开"：改的同时必须在同一屏显示
**每个知识库当前实际的索引方式**（数据来自 Dify，非配置回显），并在提交前明确告知
存量文档不会自动迁移。风险没有消失，只是从"看不见"变成"看得见"。

### 五、「本部署未启用的能力」

有一类配置**为空就等于把功能悄悄关掉**，界面上完全看不出来：

| 变量 | 为空的后果 |
|---|---|
| `DIFY_DATASET_API_KEY` | 全平台租户的知识库管理直接禁用（`config.go:24-28`，`knowledge.go:88-106`，`h.dataset` 为 nil） |
| `ACEST_KB_URL` | 经验库召回与反馈整个不装配（`router/cmd/router/main.go:104,350-374`） |
| `ROUTER_INTERNAL_URL` | 平台管理页的运行开关只读镜像显示 unknown（`config.go:43-52`） |
| `WECHAT_ENCRYPTED_MODE` | 配错则微信回调验签直接失败（`gateway/internal/config/config.go:77`） |

这和 D8 是同一类病：**没配置不是报错，是功能消失**。设置页加一块「本部署未启用的能力」，
把这类东西连同原因列出来。不给改，但不让人对着一个不存在的功能找半天。

### 六、登录会话

现状（`admin/internal/config/config.go:63-64`，`internal/handler/auth.go:41,98`）：

| | 现状 |
|---|---|
| access token | 2 小时，硬编码，无环境变量可调 |
| refresh token | 7 天，哈希存 Redis，一次性、可撤销 |
| `POST /auth/refresh` | **后端已实现** |
| 门户 | 只存 access_token，`portal/` 下 grep `refresh` 零命中 |
| 存储位置 | **sessionStorage**——关标签页即失效 |

"老要重登"是两件事叠加：2 小时到期，以及关标签页就没了。

**不采用**"把 2 小时调大"：JWT 无状态，签出去撤不回来，改成 7 天等于泄露一次管半周；
而且关标签页照样丢，只治了一半。

**采用**：前端接上已有的 refresh 流程。access token 保持 2 小时短命，
401 时自动用 refresh token 换新的再重试原请求。体验变成 7 天不用重登，
refresh token 在 Redis 里可撤销、用后即删防重放。**后端一行不用改，全是前端工作。**

#### 多账号并行是一条硬约束

实测（2026-08-26，实机）：同一账号连登两次（间隔 1.2 秒），

```
先登的 access token  → /tenants  200
后登的 access token  → /tenants  200
先登的 refresh token → 后登之后仍能换新  200
```

服务端不做单会话限制：Redis 键是 `refresh:<token哈希>`，**按 token 索引而非按用户**，
登录只写不删旧的（`handler/auth.go:90`）。前端 token 存 sessionStorage，
而 sessionStorage **每个标签页独立**。两者叠加，两个标签页各登各的账号互不干扰。

**因此「记住我」不能简单地把 refresh_token 放进 localStorage**——localStorage 同源共享、
不分标签页，两个标签页会互相覆盖对方的 refresh token，多账号并行的能力就没了。

正确做法：localStorage 里存的不是一个 token，而是**一张按账号索引的会话表**，
当前标签页在用哪个账号记在 sessionStorage 里（保持 per-tab）。两个目标同时成立：
关浏览器再打开能恢复，两个标签页各用各的账号。

已知操作坑（属于浏览器行为，不修，写进说明即可）：从已登录页面「在新标签页中打开」时，
浏览器会把原标签页的 sessionStorage 复制一份给新标签页，新页会带着第一个账号的身份。
手动开新标签页粘地址则是干净的。

「客服工作台」无法并行：Chatwoot 靠 cookie 认证，cookie 整个浏览器同源共享，
两个账号先后免密跳进去，后一个必然顶掉前一个。这是 Chatwoot 侧机制，门户改不了。

### 七、「AI 设置」改名与扩容

卡片改名为**「设置」**，描述改成对得上里面实际内容的——
现在那句"系统提示词、置信度阈值、转人工关键词与屏蔽话题"漏掉了版本历史、检索 top_k、
知识库补建、满意度调研这一半。

页面内分区：

1. **回答行为**——提示词（含版本历史/回滚）、置信度阈值、转人工、屏蔽话题、等待话术
2. **满意度调研**——现有那套
3. **知识与检索**——top_k、知识库体检与补建
4. **平台运行状态（只读）**——意图分诊/场景模式当前态、本体总闸、索引方式，
   以及第五条的「本部署未启用的能力」

第 4 区是新增的关键：**能改的和被定死的必须在同一页上并排**，
否则租户永远不知道自己的边界在哪，只能在灰掉的输入框前猜。

### 八、AI 模型配置收回门户（2026-08-26 新增）

用户指出模型设置在工作台改不了。属实，而且比"改不了"更彻底：**它是编译期常量，连环境变量都不是。**

现状（`unica/pkg/difyapp/model.go:26-43`，`PlatformModel()` 硬编码）：

```
Provider     openai_api_compatible
Name         deepseek-v4-flash
Mode         chat
Temperature  0.3
MaxTokens    4096
```

不落库、无 env、无写入口——`/api/v1/platform/settings` 的 handler 第一行就是
`if r.Method != http.MethodGet`（`admin/internal/platform/platform.go`）。
门户两处只读展示（`portal/ai-settings.html:594` 标注 read-only，`portal/admin.html:1018-1025`
分组标题写着"编译期常量 · 改完需发版"），那不是保守措辞，是字面意思。

#### 推送那一半已经写好了

`PinPlatformModel`（`bridge/dify.go:711-744`）已是完整的读-改-写函数，与 `UpdateSystemPrompt`
完全同构：`GET /apps/{id}` 拿全量配置 → 只换 `model` 字段 →
`POST /apps/{id}/model-config` 整体写回。请求体字段见 `pkg/difyapp/model.go:47-60`
的 `AsModelConfig()`：`provider`、`name`、`mode`、`completion_params{temperature, max_tokens, stop}`。

它只是**只在开户新建应用时被调用一次**（`identity/dify_line.go:257`，且仅在 `appID == ""` 分支内），
存量应用故意不碰，代码注释写着 "An existing app is left alone"。全仓库仅此一个调用点。

所以缺的不是"怎么推"，是"存哪、从哪改、怎么批量重推"。

#### 照抄阶段 2 的结构

这三样的形状与提示词那轮完全一致，直接复用已验证的模式：

| 提示词（阶段 2 已做） | 模型（本条要做） |
|---|---|
| `prompt_versions` 表 | 模型配置落库 |
| `UpdateSystemPrompt` 投影 | `PinPlatformModel` **已存在** |
| 提示词落后清单 | 模型漂移清单 |
| 勾选回推 | 勾选重推 |
| `push` 审计动作 | 复用 |

**层次**：平台级默认 + 产品线可覆盖，与提示词一致。私用场景下的实际需求是
让测试线用便宜模型、正式线用好模型，两层结构正好够用，不额外增加复杂度。

#### 模型名填错会静默炸掉

供应商凭据（base_url、API Key）全靠人在 Dify 控制台配置，UNICA 一行代码都不碰——
全仓库无任何 provider / credential / model-providers 接口调用。UNICA 只负责
"把已注册的供应商选中并 pin 参数"。因此自由输入一个 Dify 里不存在的模型名，
推送可能返回成功，但对话时才失败。

**取「先验证后提交」，不做可用模型下拉。** 写入时先推给一条产品线，Dify 认了才落库再批量推，
不认就报错且不落库。理由：可用模型列表要从零新写一整块调 Dify provider 接口的代码，
而先验证后提交把错误提前到提交那一刻，即时可见，成本几乎为零。

#### MaxTokens 不是随便填的

`model.go` 里那行注释记着：4096 是试出来的，**1024 会因"先吐推理再吐答案"被截断成空回复**，
2048 仍不够长回答。这是个推理模型。给改可以，但界面上必须把这句话摆出来，
而不是让人对着一个空白数字框猜。

## 明确不做

- **知识库、确定性事实并入设置页**：前者是内容资产、日常高频上传维护，
  后者是内容编辑（写 YAML、发布、回滚），都不是"拧开关"，频次和心智模型都不同。
- **渠道接入并入设置页**：它确实是配置，但属于"接一次不再动"的接入配置，
  与"随时要调"的回答行为不是一类，并进去只会让设置页变长。
- **租户自带模型 key（`plan-config-surface.md` 阶段 5 / 方案 C）**：私用前提下没有意义，
  仍不做。注意区分：2026-08-23 拍板的"只做方案 B"含两层意思——不做租户自带 key（保留），
  以及门户上模型一切只读（**本文第八条推翻**）。
- **调 Dify 的 provider / credential 接口**：供应商凭据继续在 Dify 控制台手工配置。
  模型的可用性改由"先验证后提交"保证，见第八条。
- **分段编辑**：分段是索引产物，改它等于重新索引，属内容资产，留在 Dify。
