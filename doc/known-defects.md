## D1 调研发出后没人把超时的那些翻成 `no_response`

> **2026-10-08 本轮已修（代码，未提交，待实机）**：`router/internal/survey/timeout.go` 的
> `SweepTimedOut` 每分钟扫一次 `survey_status='sent'` 的会话，Redis 待答键已不存在的
> 翻成 `no_response` 并 `SurveyTimeoutTotal.Inc()`（按产线打标签）；`Router.Start` 起该循环。
> "超时"以待答键是否还在为准，而不是用 `survey_sent_at` 加当前配置重算：待答键的 TTL
> 就是发出时该产线的 `timeout_hours`，回复也只认这个键，二者口径一致；改过超时配置时
> 重算会把仍可回答的调研误判为超时。UPDATE 带 `AND survey_status='sent'`，与回复竞争、
> 多副本并发时每条只计一次。schema 无需改动：`survey_status` 是无 CHECK 的 `VARCHAR(20)`，
> `no_response` 本就在迁移 005 的取值注释里。Redis 读失败时整轮停下、不翻任何一条。
> 单测（打桩库 + miniredis）覆盖：只翻过期的、不碰仍在窗口内与已完成的、二次扫描不重复计数、
> Redis 不可达时不翻。未验证：真实库上的 SQL 与真实调研流量。

> 本条原文是"满意度调查从未真正发出"。**发不出去与收不回来这两半已于 2026-08-24 修复并实机验收**
> （空闲清扫补上 `OnClose`；会话查找在调研待答期内把已关会话认回来，
> 见 `state/manager.go` 的 `fireOnClose` 与 `GetConversationByCustomer` 注释）。
> 剩下的是下面这一条，它不影响客户，只影响统计口径。

调研发出时写 `survey_status='sent'` 与一个带 TTL 的 Redis 待答记录。
客户回复则翻成 `completed`；**不回复的那些，Redis 键静默过期，数据库里的 `sent` 永远留着**。
全仓库没有任何地方写入 `no_response`（只在迁移注释 `005_survey.sql:6` 出现过），
指标 `SurveyTimeoutTotal`（`metrics/metrics.go:219-221`）定义后从未 `Inc()`。

**后果**：`survey_status` 分不出"还在等"和"等不到了"，回收率算不出来；
超时数永远是 0，看板上看不出调研是否石沉大海。**不影响客户收到什么**。

**修的方向**：起一个扫描任务，把 `survey_sent_at` 早于本产线 `timeout_hours`
且仍为 `sent` 的翻成 `no_response` 并 `SurveyTimeoutTotal.Inc()`。
注意时长是产线级配置，不能写死。

## D2 坐席在 Chatwoot 点"解决"不会关闭 UNICA 会话

> **2026-10-08 本轮已修（代码，未提交，待实机）**：网关收到 `status=resolved` 后不再写
> `unica:outbound`，改写 `unica:handoff`（`type=event.conversation_closed`）；router 的
> handoff 消费者（`handoff/consumer.go`）识别该类型后调用 `TransitionState(..., closed)`，
> 与空闲清扫走同一条关闭路径（含 `OnClose`，即满意度调查）。会话已关闭视为正常（清扫先到、
> 重投、Chatwoot 反复解决），不进死信；其它失败（如会话仍 `pending`、库不可用）写入
> `unica:dead-letter`。测试：网关侧断言出站流为空、handoff 流有一条且载荷正确；router 侧
> 打桩断言关闭调用、已关闭不进死信、失败进死信。
> **部署注意**：网关与 router 需同批升级——旧 router 会把这条关闭事件当作转人工事件处理
> （`product_line_id` 为空，会在读 Chatwoot 配置处失败并被确认掉，不会建单，但会白跑一次摘要）。
> **行为变化**：解决后客户再发消息，会话由 closed 重新进入 AI 处理，而不是继续留在人工
> 直到空闲超时；这是"已解决"本来的含义。

`gateway/internal/webhook/chatwoot.go:247-302` 收到 `status=resolved` 后构造
`type: "event.conversation_closed"` 事件 XADD 进 **`unica:outbound`**——
和客户消息共用一条流。但该事件的 `Data.ChannelID` 从未填充，
而这条流唯一的消费者（`gateway/internal/stream/consumer.go` → `adapter/registry.go:56-73`）
的逻辑是"按 ChannelID 查渠道适配器并发送"。

ChannelID 为空 → `no adapter registered for channel` → 重试三次
（`dedup/retry.go:49-77`）→ 进死信队列 `unica:dead-letter`。

全仓库没有任何消费者把 `event.conversation_closed` 转成状态转移。

**后果**：会话只能靠空闲超时（默认 30 分钟）关闭。坐席的显式"已解决"信号
完全丢失，且每次都往死信队列里灌一条。

**修的方向**：该事件不该走出站流，应走 handoff 流或独立通道，
由 router 消费并调用 `TransitionState(..., StateClosed)`。修好后 D1 也一并有了触发源。

## D8 存量产品线的知识库仍未接线、仍是关键词索引（已解，2026-08-25）

**2026-08-25 解掉**：根因是 `provisionDifyLine` 的幂等早退只看 `dify_agent_id`，
"有 app 无 dataset"因此是一个重跑开户也走不出去的死状态，而 `CreateDataset`

修法不是换一个早退条件——换成"两个都在才早退"会让缺 dataset 的线重新走完整个流程、
**再建一个 app**。整体早退被取消，改为逐项自查（见 D7 的判据修订），
开户从"全建或全不建"变成"把这条线补齐到规范"，补建入口与开户是同一段代码。

新增：`POST .../ai-settings/knowledge/provision`（仅 admin，幂等）、
诊断卡上的按钮、以及平台侧 `GET /api/v1/platform/knowledge` 就绪度清单。

实机（本地 WSL，10 条产线）：三条零售线逐条补建，`app=already`（**没有再建第二个应用**）、
dataset/binding/attach/retrieval 全部 done；再跑一次全部 `already`、`provisioned=false`。
**证明它真的被用上**：给 FreshMart 传一篇只有它答得出的文档，测试消息召回 6 段、

由此产生一个连带问题：提示词规则 9 写的是"按**参考知识**里的分场景必问项清单采集"，
对这三条线是**悬空引用**——那份知识不存在。当期的绕行办法是把采集清单写进
**本体**（无条件注入 facts_context，不依赖检索命中），见
`deploy/config/ontology/{megastore,techzone,freshmart}.yaml` 的采集属性。
这个绕行其实比放知识库更可靠，但它掩盖了本条缺陷：这三条线依然没有任何
可检索的业务知识，客户上传的资料依然无处可去。

**2026-08-22 补充：查明"为什么重跑开户也补不上"。** 开户接口整体是幂等的、
重 POST 即续跑，唯独 Dify 这一步的早退条件写错了粒度——
`tenants_provision.go` 的 `provisionDifyLine` 只看 `dify_agent_id` 非空就直接
返回 `provisioned=false`，根本不检查 dataset。于是"有 app、无 dataset"这个
恰好是三条零售线的状态，成了续跑逻辑的盲区：无论重跑多少次都走不到建库那一步。
实测（重跑五条线开户）三条线返回 `dataset_id: ""` 且无任何告警，与预期一致。
**根治**：把早退条件改为 app 与 dataset 都在才跳过，缺哪步补哪步；
届时重 POST 开户即可自动补齐，无需手工调 Dify 接口。

## D9 没有嵌入模型时，知识库静默降级为一个查不准的关键词库

**2026-08-25 现状更新**（缺陷未解，但两种失败模式要分清）：当前部署的嵌入模型
（本地中文向量模型）已可用，`DIFY_INDEXING_TECHNIQUE=high_quality`，
XDYX / AJYJ 与本轮新建的三条零售线都是 high_quality + 语义检索。
但**代码从不探测嵌入模型是否真的可用**，纯靠这个 env 手工声明，于是有两种相反的失败：
声明 `high_quality` 而工作区没有嵌入模型 → Dify 直接拒绝上传（`provider_not_initialize`），
是**显性**失败；为规避该报错把它改成 `economy` → 上传与索引全部"成功"，
关键词检索大量零命中，体检全绿无报错，才是本条说的**静默降级**。
换句话说：这条缺陷的触发条件不是"没有嵌入模型"，而是"没有嵌入模型**且有人去改了那个 env**"。

`DIFY_INDEXING_TECHNIQUE=economy` 是工作区没有嵌入模型时的唯一选择
（`high_quality` 会被 Dify 直接拒绝）。但 economy **不是** high_quality 的
廉价等价物：它按段抽取有限个关键词建倒排，没被抽中的词无论出现多少次
都检索不到。中文里这包括绝大多数专有名词和复合词——它们不是单个 token。

2026-08-12 实测（房产知识库，16 篇文档，economy）：

```
查询「青溪墅园」→ 零命中   （该词在目标文档中出现 3 次）
查询「物业费」  → 零命中   （5 篇房源文档都含此词）
```

**后果**：上传成功、`indexing_status` 全部 completed、知识库各项体检正常，
但大量真实问题得到"我这边没有这个信息"，或者拿到**邻近记录的数据**
（把 A 楼盘的物业费当成 B 楼盘的答出来）。这与 D8 是同一种失败形态：
一个看起来健康、实际在产出错误答案的系统，没有任何一处报错。

**已做的缓解**：admin 启动时若为 economy 会打 WARN
（`ai_config.go:NewAIConfigHandler`），说明这是一个关于回答质量的决定，
不再只存在于设环境变量那个人的记忆里。

**根治**：配一个文本嵌入模型并切 `high_quality`。
`deploy/embeddings/` 提供了一个自带的本地方案（本地中文向量模型 +
OpenAI 兼容端点，无需外部厂商与额外 key），实测切换后上述零命中查询
全部命中且目标文档排第一。**当前只在演练环境手工起着，未纳入编排**——
生产部署需要把它放进 compose/k8s 并加鉴权，见该目录 README 的
「生产部署注意」。在那之前，任何新部署只要没人记得起这个服务，
就会重新落回 economy。

## D10 追问丢主语，检索返回别的记录，模型照单全收（长对话最严重）

> **2026-10-08 已覆盖于 `c995976`（默认关，待实机）**：依据是该提交的 `pkg/domain/subject.go`、
> `router/internal/routing/subject.go` 及其测试，和 admin 侧 `aisettings/subjectcarry.go`。
> 走的是下文方向 2 的变体：追问缺主语时，用客户**原话里说过的对象**补全检索与模型的 query；
> 判定、落库、经验回写一律用原文；对象名清单由运营手填（只填名称）。没有选方向 1（多一次模型调用）。
> 未验证：开关默认关，下文那段 21 轮长对话没有在开启后重跑过，所以"华亭书苑"一例是否修好
> 目前没有证据。

2026-08-13 21 轮长对话实测（`doc/test-ajyj-kb-import.md` §七）。客户先锁定
「华亭书苑」聊了几轮，然后问：

> 物业费多少？车位怎么解决？

这句**不含主语**——真人对话里指代是常态。检索是无状态的，只看到这一句：

| 检索词 | 第 1 名 |
|---|---|
| `物业费多少？车位怎么解决？`（客户实际说的） | 苏河湾一号，**华亭书苑前 4 名都进不去** |
| `华亭书苑物业费多少？车位怎么解决？`（补上主语） | 华亭书苑 0.657 ✅ |

于是模型拿到的是**另一套房源**的段落。而它的对话上下文里明明白白写着
正在聊华亭书苑，它就把检索来的数据安到了华亭书苑头上，答出
「物业费3.6元/㎡/月、产权车位约60万元/个」——前者知识库里不存在（华亭书苑
是 1.5 元），后者是苏河湾一号的车位价。**置信度 0.9。**

**为什么这条最重要**：它与领域无关，与知识库质量无关，只要是多轮对话就会
发生。"那个多少钱""它保修多久""这款支持吗"——中文口语几乎不重复主语。
单轮测试永远测不出来，因为每个问题都自带主语。

**修的方向**（三选一，都是有代价的取舍，需决策）：
1. **检索前改写查询**：用会话历史把追问补成独立问题再检索。业界标准做法，
   效果最直接；代价是每轮多一次 LLM 调用（延迟+成本），或用小模型/规则降本。
2. **把已确立的主语作为检索约束**：会话状态里记住当前讨论对象，
   检索时拼进查询或作为元数据过滤。比 1 便宜，但要维护"当前对象"的状态机，
   且客户中途换对象时要能跟上。
3. **提示词兜底**：要求模型核对检索内容的主语是否与对话对象一致，不一致
   就不用。零成本但不可靠——正确数据根本没被检索到，模型最多只能改成
   "我不确定"，答不出正确答案。

单靠 3 不够。建议 1 或 2，1 更稳，2 更省。

## D11 知识库来源的内容没有任何事实校验

> **2026-10-08 部分覆盖于 `c995976`（默认关）**：依据是 `pkg/domain/commitment.go` /
> `figures.go` 与 `routing/judge.go` 的接入。承诺/金额防火墙开启后，答复里的承诺句与带单位数字
> 必须在检索原文、本体渲染或已校验 claim 里找到同值同单位的出处，否则扣下交人工；`scope=money`
> 时任何无出处的金额/比例/折扣都扣。这正是下文"数值必须在检索片段里逐字出现"的长期方向。
> **未覆盖的部分**：非数值的事实（产地、规格名、条款文字）仍无校验；有出处不等于出处对
> （D10 那种错配到另一条记录的数字，若另一条记录里确有该数字，仍会放行）。

`pkg/domain` 的 claim 校验只覆盖 **ontology 属性**：解析回答里的
`[FACT:属性=值]` 标签，比对断言、range、伴生要求。知识库（Dify dataset）
来的内容**完全在校验范围之外**——模型不为它打标签，校验器也无从比对。

D10 那次对话里模型编造了物业费、错配了车位价、还凭常识虚构了一整张税费表
（见 D12），`claim_violations` 表记录数为 **0**。

**后果**：房源明细、商品参数、订单条款——凡是放在知识库而非 ontology 里的
内容，一旦被错误检索或被模型润色，没有任何一层会发现。而这恰恰是
最容易被 D10 污染的那部分内容。

**修的方向**：短期把最关键、最不能错的事实上移到 ontology（本次测试已按
此分工：政策进 ontology、房源明细留知识库，政策类回答全部正确）。
长期需要一种针对检索内容的校验——例如要求答案中的数值必须在检索片段里
逐字出现，否则标记。后者是新机制，需单独设计。

## D12 知识库明确说"要咨询"的事，模型会自己编出一张表

> **2026-10-08 部分覆盖于 `c995976`（默认关）**：依据是 `pkg/domain/commitment.go` 的
> `deferralPattern`（需咨询/建议咨询/以…为准/另行核定/需按最新政策 等）：检索原文含这类说法时，
> 答复给出的数字一律扣下交人工，原因写明"知识库写明此类数字需咨询"。这是判定层兜底，
> 不是下文建议的提示词指令。**未做**：下文那次长对话未在开启后重跑；提示词规则 7 的风险
> 仍未单独验证；"免征"这类不带数字的矛盾说法不在数字防火墙的覆盖范围内。

同一次长对话，客户问「税费大概多少？」。知识库对该房源只写了
「非满五唯一，涉及增值税及附加，具体税费需按最新政策计算，建议客户在
签约前咨询公司法务或税务部门」，ontology 里没有任何税率。模型输出了：

- 一张含契税 1.5%、个税 1%、名下有房 3% 的费率表——**这些税率全库皆无**
- 「增值税及附加：**免征**，房本满5年可免征」——**与知识库的"非满五唯一"直接矛盾**
- 「合计预估约13万元起」

置信度 0.9。这违反提示词规则 2（不得用行业常识替客户补答案）与规则 4
（没有的具体数值不要编造）。同一次对话第 20 轮它又正确说出"非满五唯一"，
即**同一会话内自相矛盾**。

**一个必须承认的关联**：2026-08-12 为治"该答不答"新增的规则 7
（"能答就直接答"）与规则 4 存在张力。规则 7 的措辞已限定"在以上约束内
能回答的问题"，但本例说明这个限定不足以压住模型在**部分检索到相关内容**
（它检索到了别的房源的税费说明）时的补全冲动。是否由规则 7 引入无法在
无 A/B 的情况下断定，但它必须列为规则 7 的已知风险并在下次改提示词时验证。

**修的方向**：给"应当拒答"的情形一条与规则 7 同等强度的正向指令——
例如"知识来源本身写明需要咨询/以核定为准的事项，只复述该指引，
不得给出任何自行推算的数值或税率"。改完需重跑本例验证。

## D14 分档赔付政策不做区间计算，直接跳到最宽的档位（XDYX 已缓解，其余产线仍暴露）

2026-08-13 XDYX 金标 `xdyx-20`，两种分诊模式下**均稳定复现**。

客户输入：「说好次日18点前送到，结果拖到第三天中午才到，怎么补偿？」

承诺时段结束为次日 18:00，实际送达第三天中午 12:00，实际延误 **18 小时**，
落在「超 12 小时未超 24 小时 → 补 10 元无门槛券」这一档。

模型答：「根据您的描述，配送延误**已超过24小时**……该订单将全额退款，
且已送达的货物无需退回。」——**凭空把 18 小时算成超过 24 小时，直接跳到最宽档**。

值得注意的是它对规则本身记得很牢：同一条答复里完整复述了五类免责情形
（恶劣天气、大促顺延、不可抗力、客户方原因、主动改约），本体注入无问题。
错的只是**没有做那一步减法**。相邻用例 `xdyx-14`（10 斤坏 1.2 斤、允许 5%、
应赔 0.7 斤）与 `xdyx-16`（缺 3 两未达 5% 门槛）在同轮里都算对了，
说明模型能做算术；差别在于 14/16 的数字直接出现在问句里，
而本例需要先把「次日18点」和「第三天中午」换算成小时差**再**对档。

这类错误单向偏向多赔（全额退款 vs 10 元券），是会直接产生资损的错法。

**已做的修复（2026-08-13，本体 v2）**：在属性 `延误补偿分级` 里加入强制指令——
「必须先算出实际延误小时数、在答复中写明这个数值，再据此对档，严禁凭主观印象跳档」。
修完模型确实开始写出计算过程，`xdyx-20` 连跑三次全对，`xdyx-21`（台风免责）未受波及。

修复过程中的一个副产物：改完后模型写出"延误时长约为42小时"，
查下来不是算术错误，而是原问句"次日18点→第三天中午"存在中文序数日歧义
（把哪天算第一天，答案是 18 或 42 小时）。金标已改为绝对日期。
**给后续写用例的提醒**：考区间计算的题，题面不要同时考日期表述消歧。

**为什么不从本文件删除**：修的是 XDYX 租户的本体措辞，**产品代码一行没动**。
凡是"按区间/阈值分档"的政策都有同样的跳档风险，其余四条产线的本体里
没有这句强制计算指令，仍然暴露。彻底的修法应当在提示词层面统一要求
"对档前先算出并写明区间值"，而不是逐个租户在本体里补一句。
待该通用修复落地并复跑四条线后，本条方可删除。

## D15 开户不写 ontology 配置键，发布的本体在实机链路上从不生效

2026-08-13 XDYX 多轮测试首轮发现。**离线金标完全看不出来**，这是本条最值得记住的地方。

现象：多轮测试 10 轮里 10 轮都以 `reason=low_confidence` 转人工，
连"退款一般多久到账？"这种纯政策问题都被拦成转人工。
而同一时刻 `evalset -line XDYX -inject-facts` 跑 29/29。

根因：`product_lines.config_json` 缺 `ontology` 键。对照 AJYJ：

```json
"ontology": {"validation": "shadow", "inject_facts": true}
```

XDYX 走正式开户 API 创建，这个键**开户流程根本不写**。
本体照常发布、`active_version` 照常推进到 v2，但实机路由从不注入
facts_context，`GroundedConfidence` 拿不到事实注入的加成，
置信度稳定落在 0.45~0.60，全线低于 0.70 阈值。

**为什么离线测不出**：`evalset -inject-facts` 是由命令行开关强制注入的，
不读 config_json 这个键（这是刻意设计，为了做注入与否的 A/B）。
于是形成一处离线/实机口径分叉：**离线跑分越好，越掩盖实机根本没注入这件事**。
AJYJ 那轮之所以没暴露，是因为它的这个键是当时手工补上的。

检索本身没问题——日志里 RAG 命中的是正确文档（`XDYX-DOC-PICKUP-EXCEPTION`
score=0.624、`XDYX-INTAKE-DROPOFF` score=0.571），坏的只是置信度构成。

**修的方向**：开户流程（`identity/tenants_provision.go` 一线）应当在创建
产品线时就写入 ontology 默认配置，或者在本体首次发布时自动补齐——
发布了本体却不注入，没有任何合理场景。
在此之前，任何新开租户都必须手工补这个键，否则实机表现与跑分完全对不上。

**顺带查出并已修复的第二个问题**：`[handoff] summary generation failed:
product line 5cfe1cf4-... has incomplete dify config`。查下来不是配置没写，
而是**读错了地方**——`handoff/summary.go` 去读 `config_json` 里嵌套的
`dify.base_url` / `dify.api_key`，而凭证一直存在 `product_lines` 的
`dify_base_url` / `dify_api_key` **列**里（evalset 和路由都读列）。
那个嵌套键任何代码都没写过，所以**所有产线的转人工摘要一直在走 fallback**，
从来没有真正生成过。

这条在本次需求下从"体验瑕疵"升级成"直接拆台"：采集规范的全部意义就是让
人工接手时不必重复询问，而摘要恰恰是那些信息送到坐席眼前的载体，
摘要不生成等于白采集。已改为读列、config_json 仅作手工覆盖，
`go test ./internal/handoff/...` 通过。

**后果**：三条零售线错过了规则 6（应答策略不得改变可陈述内容）和规则 7

## D18 max_tokens 耗尽时答复整条丢失，链路当作正常答复照发

> **2026-10-08 核对：已覆盖于 `3e7174d`**（下文"未根治的部分"已过时）。依据：
> `routing/judge.go` 末尾的检查——`domain.IsBlankAnswer(j.Answer)` 且判定为投递时改为
> `handoff`（原因 `empty_answer`；模型自己请求过转人工则保留原因），不代填任何话术；
> 谓词覆盖零宽字符、BOM 与标签剥离后只剩标点的情形；`judge_empty_test.go` 钉住"凡投递必非空"。
> 本轮 D20 让全角标签也能被剥离，只含全角标签的答复剥离后为空，同样被拦下（`judge_tags_test.go`）。
> 未验证：真实流量里空答复转人工的实际发生情况。

**形态**：平台当时声明的模型会先输出推理内容再给答复。当
`max_tokens` 不够走完推理，生成在"还在想"的阶段就被截断，
Dify 返回 **`answer: ""`**——不是被截短的半句话，是**一个字都没有**。

而链路把空答复当作一次正常应答：`handoff=false`、`escalated=false`、
不告警、不兜底、不转人工。客户那端收到的是一片空白。

**证据**（2026-08-23，XDYX，`max_tokens: 1024`）：

```
Q: 我出差了三天没去取，柜子里的水果全烂了，这算谁的责任？
   completion_tokens=1024  answer_len=0     ← 精确撞满上限
Q: 取货柜的制冷坏了…算谁的责任？
   completion_tokens=1024  answer_len=0
Q: 到货挑出来1.2斤是坏的，能赔我多少？
   completion_tokens=970   answer_len=84    ← 未撞上限，正常作答
```

五线全量 125 条里 **18 条答复为空**。把上限抬到 4096 重放，同样的问题
不但有答复，而且答案是对的（"属于客户责任"、"责任由公司承担"、
"批次抽检参考值不作承诺"）——**这批失败与模型能力无关，是被上限掐死的**。

实测各条真实需要的 completion tokens：386 / 1317 / 1380 / 1757 / 2021。
**2048 仍会掐掉最长的那条**，故取 4096。

**已处置**：五条产线 `max_tokens` 统一改为 4096（`tmp/unify_model.py`）。

**2026-08-26 补记，处置范围比当时以为的窄**：上面那次处置用的是一次性脚本，
只覆盖了参与跑分的五条线。模型漂移清单上线当天（配置面重构阶段 4）实机一查，
**演练线 DrillCo / DrillCo2 / DrillCo3 / DrillCo4 / DrillCo5 五条根本没被扫到**：
它们跑在工作空间默认的另一个模型上而不是平台声明的模型，且 `temperature` 与 `max_tokens`
双双为 0 —— 即 `completion_params` 从未被写过，一直吃 Dify 工作空间的默认值。
这正是 `pkg/difyapp/model.go` 顶部注释记的那笔账（"nothing wrote
model_config["model"] at all, so every app inherited whatever the Dify workspace
default happened to be"），它从未被清掉，只是没人再看。

根因不是脚本漏了谁，是**处置手段本身是一次性的**：`PinPlatformModel` 全仓库只有
开通新应用时一个调用点，存量应用一律不碰，于是任何在脚本之后新建的、
或脚本当时没列进去的线，都会重新漂回工作空间默认值而无人知晓。
阶段 4 把这条路补成常规能力——漂移清单逐线读 Dify 实况比对，
勾选即可重推，写审计——并已借它把上述五条线纠正到平台声明的模型 / 4096。

**未根治的部分**：空答复本身仍会被照发。参数调大只是把触发概率压低——
问题更长、知识库更大、推理更绕的时候还会撞上。真正的修复是
**在链路里把"空答复"当成失败**：判定层遇到 `answer == ""` 应当直接转人工，
而不是把空字符串投递给客户。这条比调参重要，因为它是**静默**失败。

## D19 金标对"空答复"没有断言，什么都不说也能通过

> **2026-10-08 核对：已覆盖于 `3e7174d`**。依据：`router/internal/eval/assert.go` 在所有
> `must_*` 断言与转人工短路之前无条件检查 `domain.IsBlankAnswer`，只有"用例要求转人工且实际转了"
> 才允许空；`cmd/evalset` 与重放都经 `JudgeAnswer` 后再断言。`assert_test.go` 有

> `BlankAnswerWithheldByRouterStillFails` 等用例。本轮未改动该执行器。

D18 那 18 条空答复里，**有 6 条被金标判为通过**
（`ajyj-14` `ajyj-15` `ajyj-19` `ajyj-23` `fresh-20` `xdyx-23`）。

原因是这些用例的期望只有 `must_not_contain` 或 `handoff` 一类**否定式断言**——
一条空答复天然不包含任何禁止措辞，于是全部满足。其中 `ajyj-14/15`、`fresh-20`

**根治**：断言层加一条无条件前置检查——**非转人工的用例，答复不得为空**。
这是所有 `must_*` 断言的公共前提，不该逐条去写。

## D20 标签协议只认半角方括号与半角冒号，全角写法原样投给客户

> **2026-10-08 本轮已修（未提交）**：三套协议不再各持一份正则，统一走 `pkg/domain/tags.go`
> 的 `ScanTags`：括号认 `[ ]`、`［ ］`、`【 】`且可混配，分隔符认半角/全角冒号，名称不分大小写，
> 名称、分隔符、值两侧的半角空白与全角空格都容忍；`[FACT:]` 的等号认半角/全角。剥离是全量的
> （畸形标签也剥），解析由各协议决定；名称后紧跟字母、数字或下划线的（如 `[FACTORY]`）不算标签。
> `ParseClaims` / `ParseEscalation` / `marketing.DetectIntents` 已改用它。单测：`tags_test.go`
> （半角/全角/混合/空白 × 三协议、非标签不误伤、未闭合标签不吞掉后面的标签）、
> `detector_test.go`、`routing/judge_tags_test.go`（全角 `HANDOFF` 照常升级且原因为 payout）。
> 仍不认的写法：`<HANDOFF>` 这类尖括号、全角字母拼的标签名。

三套标签协议（`[HANDOFF:原因]`、`[FACT:属性=值]`、`[INTENT:意图]`）的识别正则
要求 ASCII 方括号与半角冒号。中文输入法下模型写出全角形式时：

- `【HANDOFF:payout】`（全角方括号）：**不识别、不剥离**。客户直接读到内部标记，
  同时这次升级被整个吞掉——一条要钱的对话没有任何人接手。
- `[HANDOFF：payout]`（全角冒号）：会被宽剥离模式吃掉，但原因值解析失败，
  降级为 `other`，坐席拿不到分类。

2026-08-23 已修的只有**大小写**（三处正则加 `(?i)`，`[INTENT:]` 捕获值补
`ToLower`）：`[handoff:payout]` 此前同样不识别不剥离，属同一形态。

**为什么不再打一个正则补丁**：这已经是第四层字符类补丁了。
每加一种写法就要同步改三处正则、三份测试，而下一种写法（半角括号配全角冒号、
标签内有空格、模型用 `<HANDOFF>` 之类）随时会出现。
根治是把标签识别抽成一个规范化步骤——先把全角标点归一到半角、再统一匹配，
三套协议共用同一个解析器，而不是各自维护一份正则。

**与 D18 的关系**：同一类故障——不该到客户眼前的东西到了客户眼前。
D18 的修复（`pkg/domain.IsBlankAnswer`）能兜住"剥离后为空"的情形，
但兜不住"根本没被剥离"——那种情况下答复非空，只是内容是内部标记。

## D22 同一秒内两次登录拿到完全相同的 token（已解，2026-09-02）

JWT 载荷里没有随机标识（`admin/internal/auth/jwt.go:51` `GenerateTokenPair`），
同一用户在同一秒内登录两次，`iat` 与 `exp` 都相同，签出来的 access token 与 refresh token
**字节级完全一致**。2026-08-26 实机复现：连续两次登录返回的 token 字符串相同；
间隔 1.2 秒后再试则不同。

后果限于 refresh 一侧：Redis 键是 `refresh:<token哈希>`（`handler/auth.go:90`），
两个会话共用同一个键，而 refresh 是一次性的（用后即删，`auth.go:131`），
于是先用掉的那个会话把另一个会话的续期能力一起废掉。

现在影响很小——要在同一秒内登两次同一账号才会撞上。但一旦前端接上自动续期
（`doc/plan-workbench-settings.md` 第六条），并发刷新就可能踩到。
根治是签发时加一个随机标识，让每次签发必然唯一。

**已解（2026-09-02）**：`GenerateTokenPair` 现在给 access 与 refresh 两组 claims 各填一个
独立的 `jti`，值取 `crypto/rand` 的 16 字节转 hex。随机源失败时返回错误而不是退化成空串——
一个空的或可预测的 `jti` 就是这条缺陷换了件衣服。单测 `TestGenerateTokenPair_UniquePerIssue`
断言连续两次签发的两个 token 均不同、`jti` 非空、且同一对里 access 与 refresh 的 `jti` 互异。

实机复现验证（换二进制后）：连续两次登录，access 与 refresh 全不同，
三个 `jti` 两两不同。此前预判的"前端接上自动续期后并发刷新会踩到"没有发生——
D 组的续期上线时这条已经先修掉了。

> 兼容：无 `typ` 的旧 access token 照常接受直到过期（它一定带 role，`users.role` 非空）；
> 无 `typ` 且无 role 的旧 token 只可能是旧 refresh token，作 Bearer 时拒绝，但在 `/auth/refresh`
> 仍可正常换取（该端点不经中间件，靠 Redis 里登记的 refresh 哈希判定），换回的是带类型的新一对，
> 所以一个 refresh 有效期之后不再有无类型 token。`/auth/refresh` 只认 refresh 这一半无需改代码：
> access token 从未登记进 `refresh:<哈希>`，本来就会被拒。单测覆盖：新签发的类型、refresh 作 Bearer
> 被拒（401）、旧 access 接受、旧 refresh 作 Bearer 被拒且仍可解析、未知类型被拒。

`AuthMiddleware`（`admin/internal/auth/middleware.go:80-106`）只校验签名，不区分
token 类型。refresh token 与 access token 用同一把密钥签发、载荷结构相同，
于是把 refresh token 放进 `Authorization: Bearer` 里能通过鉴权。

2026-09-02 实测（rehearsal 管理员与 AJYJ 租户用户各一次）：

| 路由 | access token | refresh token 当 Bearer |
|---|---|---|
| `/api/v1/tenants` | 200 | **403**（`RequireAdmin` 挡下） |
| `/api/v1/platform/settings` | 200 | **403** |
| `/api/v1/audit-logs` | 200，119 条 | **200，但 `{"entries":[],"total":0}`** |

**没有数据泄露**：refresh token 的 `role` 与 `tenant_id` 都是空串，
只挂 `AuthMiddleware` 的 `/api/v1/audit-logs` 按空租户过滤，结果是零行而不是全部。
所以这是类型卫生问题，不是机密性问题——这也是它被判低危的理由。

**为什么仍然该修**：D 组之后 refresh token 会在勾了「记住我」时进 `localStorage`
并存活 7 天，比 access token 长得多。它现在多出一份"能通过鉴权"的能力，
是没有任何地方需要、却随时可能被下一条路由的默认行为放大的多余权限。
根治是签发时加一个 `typ` claim（access / refresh），`AuthMiddleware` 只认 access，
`/auth/refresh` 只认 refresh。
