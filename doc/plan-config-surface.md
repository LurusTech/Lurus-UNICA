# 配置面重构方案

> 目标：把"改一件事得先知道它属于哪个技术组件"变成"改一件事只需要知道它归谁负责"。
> 本文只做设计，不含实现。盘点依据为 2026-08-22 的全仓库配置项清点。

---

## 一、诊断：乱在哪里

现状不是随机堆叠，有五条结构性成因。

**成因 1：落点按"谁先写了代码"划分，不是按"谁承担后果"划分。**
小红书渠道凭证在数据库、可在门户改；微信/淘宝/快手的凭证在 env、门户明确拒绝建行。
两者敏感度相同、责任主体相同，差别只是动态渠道那条先做了。
`config_json.survey`（满意度调研的开关与触发门槛）router 在读、全仓库没有任何写入接口；
`holding_message` 有字段、有解析、有回填，就是没有入口。这些不是遗漏，是"配置项由实现
顺手产生"的必然结果。

**成因 2：外部系统同时是执行引擎和配置库，权威源因此漂移。**
系统提示词**只存在 Dify 里**，UNICA 没有本地副本。后果是：无法审计谁改的、无法版本回滚、
无法知道哪个租户漂了、批量回推只能靠一次性脚本。每个应用绑定的模型与推理参数同理——
代码往 Dify 应用只写 `prompt` 一个字段，其余 model_config 完全不碰，于是出现了
**五条产线跑着两个不同模型而无人知情**（三条零售线 deepseek-v4-flash / temp 0.3 /
max_tokens 1024，XDYX 与 AJYJ 是 deepseek-chat + Dify 默认参数），基线文件却叫
`baseline-deepseek-v4-flash.json`。
反例是本体（ontology）：有本地版本表、有 publish/rollback——这是全系统唯一做对的一块。

**成因 3：把"一次性写入"当成了配置管理。**
提示词、检索方式、分段规则都是开户瞬间写一次，之后模板改了存量租户永远留在原地，
且没有任何机制会发现。D16（三条零售线的提示词停留在开户当天的版本，缺规则 6/7）与
D8（三条零售线根本没有数据集）是同一个形态的两次发作。
根因是把**默认值**与**生效值**混为一谈：模板改的是默认值，而生效值早在开户那一刻就被复制走了。

**成因 4：同一个 schema 在两个服务各写一份，靠注释约束同步。**
guardrail 的默认值与 struct 在 admin 和 router 各有一份，注释写着 "Must stay identical"。
"退款"关键词那次事故就是只改了一处：门户显示的"当前生效值"与路由实际生效值不一致，
而且运维在门户保存一次，错误的默认值会被固化写回 `config_json`。

**成因 5：分层按技术边界切，不按责任主体切。**
admin / router / gateway / Dify / Chatwoot 是实现边界。用户感受到的"叠放太乱"，
本质是他必须先做一次技术归属推理，才能找到改配置的地方。

## 二、划分原则

用两个正交维度给任何一个配置项唯一定位。

**维度 A —— 谁承担后果**

| 层 | 判据 | 界面 |
|---|---|---|
| L0 实例 | 与运行环境绑定、无业务含义 | 不进任何界面，只在 env 文件 |
| L1 平台 | 改错了会伤到**别的**租户 | 门户平台页，仅 admin；租户只读 |
| L2 租户 | 改错了只伤自己 | 门户租户页，租户自治 |
| L3 外部内容 | 是外部系统的原生内容资产 | 外部系统，定位降级为**排障与观测** |

**维度 B —— 权威源在哪**

- **本地权威**：UNICA 库是唯一真相，外部系统里的那份是投影，可随时重推。
- **外部权威**：外部系统是唯一真相，UNICA 只持有引用 ID。

由此得到五条判定规则：

1. **凡是影响回答内容与行为的配置，权威源必须在 UNICA 库**，外部系统只是执行副本。
   只有本地权威才能审计、版本化、批量回推、检测漂移。成因 2 与成因 3 都由这一条封死。
2. **凡是内容资产（文档正文、附件），权威源留在外部系统**，UNICA 只管入口与状态。
   把文档正文复制一份没有价值，只会制造新的一致性问题。
3. **凡是改错了会伤到别的租户的，一律 L1**，租户界面只读展示而非隐藏——
   看不见比改不了更容易出事。
4. **凡是与环境绑定、无业务含义的，不进任何界面**（数据库地址、JWT/AES 密钥、端口、worker 数）。
5. **凡是有业务含义的开关，不许留在 env。** env 改一次要重启、无审计、无租户粒度。

### 对原始想法的评估

| 你的提法 | 评估 |
|---|---|
| 门户作为唯一配置入口 | **成立，而且应该更强。** 你说的是"入口唯一"，但只统一入口不统一权威源，配置照样会漂——今天的模型漂移就是入口在 Dify、权威也在 Dify 的结果。规则 1 要求的是权威源回收，门户唯一入口是它的副产品。 |
| 涉及知识库的具体内容开 Dify | **部分不成立。** "知识库"里其实是两类东西：**文档正文**（该留 Dify，规则 2）与**检索方式、分段规则**（该收回门户，规则 1）。按"知识库"整块划，会把后者一起留在门户够不着的地方——那正是 D8 长出来的土壤。边界应该划在"内容 vs 参数"，不是"知识库 vs 其他"。 |
| API key 等从工作台继承 | **方向对，但"继承"这个词掩盖了一个必须先做的决策**：是租户填自己的 key，还是平台一把 key 下发、租户只读？两者成本差一个数量级。见第四节。 |
| 你没提但更该收回的 | **模型选择与推理参数。** 它比 key 更直接影响回答质量，而且现在完全无人管辖——不在门户、也不算"人去 Dify 配的"，是代码写死一次就再不过问。 |

## 三、目标形态：逐项归属

### L0 实例层（保持在 env，不进界面）

`DATABASE_URL` / `POSTGRES_URL`、`REDIS_URL`、`JWT_SECRET`、`AES_ENCRYPTION_KEY`、
各服务端口 / worker 数 / 超时 / 消费组、`GATEWAY_HOST`、分区维护参数、
`DIFY_ADMIN_*`（平台连 Dify 的管理凭证）、`CHATWOOT_PLATFORM_TOKEN`。
**全部保持不变。**

### L1 平台层（门户平台页，仅 admin 可写，租户只读可见）

| 配置项 | 现落点 | 动作 |
|---|---|---|
| 模型供应商及其 API key | Dify 控制台 | **迁移**：门户填写，由 admin 写入 Dify 工作空间 |
| **生效模型（全平台唯一）** | Dify 应用逐个手设 | **迁移 + 强制**：平台单点设定，所有产线共用一个模型，租户不可选 |
| 推理参数 temperature / max_tokens | Dify 应用（代码完全不碰） | **迁移**：随模型一起，平台级单一值 |
| 嵌入模型 | Dify 控制台 | **迁移**：同上 |
| 索引技术 indexing_technique | env | **迁移**：平台配置 |
| 默认提示词模板 | 编译进 admin 的常量 | **迁移**：平台配置表，且需暴露"存量租户与默认值的差异" |
| 默认 guardrail 值 | admin+router 各硬编码一份 | **迁移**：先合并进 `unica/pkg/`，再上提为平台配置 |
| 默认检索设置、默认分段规则 | 硬编码 / 建库时写一次 | **迁移**：平台默认 + 租户可覆盖 |
| 微信 / 淘宝 / 快手渠道凭证 | gateway env | **迁移**：平台层加密存储。这些是平台代持的应用凭证，不是租户的 |
| ACEST 外部知识库对接 | router env | **迁移**：平台集成配置 |
| Chatwoot 平台 token | admin env | **保持**（L0/L1 边界项，无界面价值） |

### L2 租户层（门户租户页，租户自治）

| 配置项 | 现落点 | 动作 |
|---|---|---|
| 系统提示词 | **只在 Dify** | **权威源迁移**：UNICA 库落本地权威 + 版本表，Dify 降为投影 |
| 模型与推理参数 | Dify 应用 | **上提到 L1**：见下方决策，租户不可选，门户只读展示 |
| 置信度阈值 / 转人工关键词 / 屏蔽话题 | `config_json.guardrail` | **保持** |
| 转接等待语 holding_message | `config_json.guardrail`，**无入口** | **补入口** |
| 满意度调研 survey.* | `config_json.survey`，**无入口** | **补入口** |
| 本体与事实注入开关 | `ontology_versions` + `config_json.ontology` | **保持**（范本） |
| 知识库文档增删 | Dify 数据集 | **保持**（规则 2） |
| 检索方式 / top_k / rerank | Dify 数据集，**建库时只写一次** | **迁移**：门户可随时改 |
| 分段规则 | 硬编码在 Go | **迁移**：租户可覆盖平台默认 |
| 小红书渠道账号 | `channel_configs` | **保持** |
| 微信 / 淘宝 / 快手渠道 | env，门户拒绝建行 | **改形态**：平台代持凭证 + 租户绑定 |
| INTENT_TRIAGE / SCENE_MODE / ONTOLOGY_ENABLED | router env | **迁移**：它们改变回答行为，属租户级开关（规则 5） |
| 违规复核 | `claim_violations` | **保持** |

### L3 外部系统（定位降级）

- **Dify 控制台**：保留知识库文档正文与索引状态明细、应用编排的调试与预览。
  定位从"配置场所"降为"**排障与观测场所**"。**租户不再需要进 Dify。**
- **Chatwoot**：坐席工作台，本次不动。

### 不可配置项（明确宣告）

食品安全 / 欺诈类升级词（`guardrail/evaluator.go` 硬编码）**保持不可配置**，
任何租户不得关闭。这不是遗漏，是刻意的安全底线，应在门户上明示存在但标为不可编辑——
让它可见，避免下一个人把它当成缺失功能补上。

## 四、API key 继承：三个方案与推荐

**必须先知道的硬约束**：Dify 的模型凭证是**工作空间级**的，应用只能从工作空间已注册的
模型里挑。五条产线目前共用一个工作空间。所以"租户自带 key"不是加个表单的事。

| | 方案 A 每租户独立工作空间 | 方案 B 平台单一凭证 + 门户只读 | 方案 C 平台代持租户 key |
|---|---|---|---|
| 做法 | 开户时建工作空间，各自配模型供应商 | 门户加只读卡片显示当前模型与供应商 | 租户在门户填 key，平台注册成工作空间级自定义模型（名字带租户前缀），把该租户应用指向它 |
| 成本 | 高：开户流程、成员管理、知识库与应用都要跟着搬 | 最低 | 中 |
| 收益 | 租户真正自带 key，费用与配额天然隔离 | 只解决"看不见用的什么模型"，不解决自带 key | 租户自带 key 且计费分离 |
| 副作用 | Dify 社区版多工作空间运维支持一般 | 无 | 工作空间模型列表随租户数增长 |
| 可逆性 | 差（要迁移应用与数据集） | 好 | 中 |

**决策（2026-08-23，已拍板）：只做 B。A 与 C 均不做。**

因为模型本身已被定为**平台级、全平台唯一、租户不可选**——不论租户在界面上设置什么，
生效的只有一个模型。这条决策直接把 A 和 C 的前提抽掉了：既然租户不能选模型，
"租户自带 key"就没有落点，也没有意义。

选择单一且**刻意不强的**模型（deepseek-v4-flash）是有意的测试策略：
强模型会用推理能力盖住提示词、检索、本体这三层的缺陷，让金标虚高；
弱模型把这些缺陷逼到台面上。跑分的目的是**发现问题**，不是拿到好看的数字。

因此门户上模型相关的一切都是**只读展示**：让租户看得见用的是什么模型、什么参数，
但改不了。看不见比改不了更容易出事，所以展示不能省。

### 随之而来的强制要求

统一模型是个**状态**，不是一次操作。当前五条线已被拉平（见下），
但开户流程创建 Dify 应用时**不写 model 字段**，新租户会落到 Dify 的工作空间默认值上，
于是又漂。所以"平台唯一模型"必须在开户流程里落地成代码，否则今天拉平、明天再散。
这一条被提到阶段 1，因为它防的是**继续产生**新的漂移。

## 六、落地顺序

每个阶段都是可独立验收的增量。

**阶段 0 —— 收敛（不改任何行为）**
做第五节的 1/2/5，删 3 的读取路径，定 4 的权威。
*验收*：五条产线的 `ai-settings` 返回值与 router 实际生效值逐项一致（写一个对拍脚本）。

**阶段 1 —— 补缺口（最小成本、最大止血）**
`holding_message` 与 `survey.*` 补写入接口与表单；门户加"当前模型 / 供应商 / 推理参数"
只读卡片（方案 B）；**开户流程写死平台唯一模型**，杜绝新租户继续漂。
*验收*：前两项在门户可见可改且 router 立即生效（路由缓存正确失效）；
新开一个租户，其 Dify 应用的 model 与平台设定一致（这是本阶段唯一的强制项）。

**阶段 2 —— 权威源回收：提示词**
提示词在 UNICA 库落本地权威 + 版本表，比照 ontology 的 publish/rollback；
Dify 降为投影，保存即推送；新增"与平台默认模板的差异"视图。
*验收*：改平台模板后能列出哪些租户落后，能一键回推。**直接解掉 D16。**

**阶段 3 —— 权威源回收：模型与检索**
检索方式/top_k/rerank、分段规则收进门户，租户级覆盖平台默认
（模型与推理参数**不在此列**，它们在阶段 1 已定为平台级只读）。顺带修 `provisionDifyLine` 的幂等早退条件
（现在只看 `dify_agent_id`，导致"有 app 无 dataset"的三条零售线永远补不上）。
*验收*：三条零售线能在门户里补建数据集并设检索方式。**直接解掉 D8。**

**阶段 4 —— env 里的业务开关下放**（可不做）
`INTENT_TRIAGE` / `SCENE_MODE` / `ONTOLOGY_ENABLED` / `DIFY_INDEXING_TECHNIQUE`
改为平台或租户级配置。
*验收*：不重启服务即可切换。收益是运维便利，不是功能。

**阶段 5 —— 租户自带 key**（可不做）
方案 C。取决于是否真的出现多个付费主体。

## 七、风险与不碰的范围

**本次不碰**：消息链路本身（网关 / Redis / router 的路由逻辑）；角色模型
（仍只有 admin 与 user，不引入第三种角色）；Chatwoot 坐席侧功能；
本体（ontology）——它是唯一做对的一块，作为范本而非改造对象。

**风险**：

- **阶段 2 的第一次推送会覆盖手改**。若某租户在 Dify 控制台里手工改过提示词，
  搬权威源时会被冲掉。必须先做全量备份 + 差异报告（形态比照既有的 dry-run 回推脚本）。
- **阶段 3 会让存量金标漂移**。检索方式与分段规则一改，检索结果就变。
  改之前必须冻结一份基线。模型统一已于 2026-08-23 完成（五条线全部
  `openai_api_compatible/deepseek-v4-flash`，temperature 0.3、max_tokens 1024），
  但**基线尚未重冻**：现有全部基线是在混合模型下跑出来的，与统一后不可比。
  重冻是阶段 0 之前就该做的事。
- **max_tokens 1024 与采集清单可能冲突**。规则 9 要求一轮最多问 3 项、
  责任定性还要给依据，1024 上限是否够用没有实测过。重冻基线时要专门看截断。
- **阶段 0 的对拍可能暴露五条线的生效值已互相不一致**。若发生，先决定"以谁为准"
  再继续，不要在对拍红着的情况下往下走。
